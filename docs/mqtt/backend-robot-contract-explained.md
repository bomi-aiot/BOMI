# MQTT 로봇 ↔ 백엔드 계약, 쉽게 이해하기

> **대체됨(SUPERSEDED):** 이 문서는 이전 계약의 설명 기록입니다. 5개 시나리오 메시지의 최종 기준은 [`scenario-contract-v1.md`](./scenario-contract-v1.md)이며, 충돌 시 해당 문서를 따릅니다.
> 이 문서는 대체된 [`backend-robot-contract.md`](./backend-robot-contract.md)를 **처음 보는 사람도 이해하도록** 풀어 쓴 설명판입니다.
> 정확한 값·흐름은 최종 시나리오 계약을 보세요. 여기서는 당시 계약을 "왜 이렇게 하는가"라는 관점에서 우편/택배 비유로 설명합니다.

## 한 줄 그림

로봇·센서와 백엔드는 **MQTT라는 우체국**을 통해 편지(메시지)를 주고받습니다. 이 문서는 "편지를 어느 주소로, 어떤 봉투에, 무슨 내용으로 보낼지"를 미리 맞춰두는 약속입니다. 약속을 안 맞추면 서로 다른 규격으로 편지를 보내 아무도 못 알아듣습니다.

---

## 1. 토픽 = 편지 주소

MQTT는 "주소"로 편지를 주고받습니다. 주소 형식은:

```
bomi/v1/{누구}/{어느 기기}/{무슨 용도}
예) bomi/v1/robot/robot-01/commands  →  "robot-01 로봇에게 보내는 명령함"
```

누가 어느 함에 넣는지만 정해두면 됩니다.

- 문/환경 센서 → `bomi/v1/iot/{센서id}/events` (백엔드가 받음)
- 로봇 상태·결과 → `bomi/v1/robot/{로봇id}/status`, `.../results` (백엔드가 받음)
- 백엔드 명령 → `bomi/v1/robot/{로봇id}/commands` (로봇이 받음)

> 핵심: **어떤 편지는 어느 주소함에 넣는다**는 목록.

## 2. 봉투 = 모든 편지에 공통으로 붙는 라벨

내용물이 뭐든, 편지 봉투 겉면엔 항상 같은 5개 라벨을 붙입니다.

| 라벨 | 쉬운 뜻 |
| --- | --- |
| `eventId` | 편지 고유번호(송장번호). 같은 편지가 두 번 와도 이 번호로 "아까 그거"임을 알아 중복 처리 안 함 |
| `type` | 편지 종류 (예: "도착 알림") |
| `occurredAt` | 언제 일어난 일인지 — **시간대까지 붙은** 시각 (`2026-07-27T15:30:00+09:00`) |
| `sourceId`/`robotId` | 보낸 기기 이름. 주소에 적힌 기기와 **같아야** 함(위조 방지) |
| `payload` | 실제 내용물(3~5장에서 종류별로 다름) |

배송 규칙 3가지:

- **QoS 1**: "최소 한 번은 반드시 도착". 대신 가끔 **같은 편지가 두 번** 올 수 있음 → 그래서 `eventId`로 중복을 걸러냄.
- **retain=false**: 브로커(우체국)에 편지를 쌓아두지 않음. 항상 그때그때 새 편지.
- 형식이 틀린 편지는 **조용히 버림**. 잘못된 편지가 무한 재전송되는 사고를 막기 위함.

> 핵심: **봉투 겉면 규격을 통일**한다.

## 3. 백엔드 → 로봇 : "이거 해라" (명령)

백엔드가 로봇에게 시키는 편지입니다. 딱 3종류:

| 명령 | 내용물 | 뜻 |
| --- | --- | --- |
| `NAVIGATE` | `target`: `ENTRANCE`(현관) / `DEFAULT`(제자리) | 거기로 이동해 |
| `SPEAK` | `text`: 말할 내용 | 이 말을 해 |
| `CANCEL` | 없음 | 하던 거 멈춰 |

여기서 제일 중요한 건 **`scenarioId`(작업번호)** 입니다. "이 명령은 **몇 번 귀가 작업**의 일부야"를 같이 적어 보냅니다. 택배 송장번호라고 생각하세요. `expiresAt`은 "이 명령 2분 지나면 무효"라는 유효기간입니다.

> 핵심: 명령마다 **작업번호(scenarioId)** 를 달아 보낸다.

## 4. 로봇 → 백엔드 : "다 했어요" (결과·상태)

로봇이 백엔드로 보내는 답장입니다.

| 편지 | 내용물 | 뜻 |
| --- | --- | --- |
| `NAVIGATION_RESULT` | **`scenarioId`(받은 값 그대로)** | 이동 끝났어요 |
| `SPEAK_RESULT` / `CANCEL_RESULT` | `scenarioId` | 말/취소 끝났어요 |
| `NAVIGATION_STATUS` | (진행 상황, 자유) | 가는 중이에요 (지금은 참고만) |
| `REST_STATE_CHANGED` | `restState`: `RESTING`/`AWAKE` | 시니어가 쉬는 중/깼어요 |

**가장 중요한 약속**: 로봇은 결과 답장에 백엔드가 보냈던 **작업번호(`scenarioId`)를 그대로 되돌려줘야** 합니다. 그래야 백엔드가 "아, 아까 그 3번 귀가 작업의 도착 알림이구나" 하고 다음 단계(인사하기)로 넘어갑니다. 번호가 없으면 어느 작업 결과인지 알 수 없어요.

> 핵심: **답장에 작업번호를 그대로 echo(반사)** 한다.

## 5. IoT 센서 → 백엔드 : "무슨 일 생겼어요" (이벤트)

| 편지 | 내용물 | 뜻 |
| --- | --- | --- |
| `DOOR_OPENED` | 없음 (보낸 센서 id가 곧 단서) | 현관문 열림 → 귀가 시나리오 시작 |
| `AMBIENT_ENVIRONMENT_OBSERVED` | `temperatureC`, `humidityPercent`, `comfortAssessment?`, `observedAt?` | 방 온·습도 관찰 |

> 핵심: 센서는 **무슨 일이 났는지**만 알려주면, 그다음 판단은 백엔드가 함.

## 6. 기기 이름 규약 = "이름표"

- **로봇**: 자기 이름표(`robot-01` 같은 `deviceId`)를 **절대 안 바뀌게** 정해 쓰기. 백엔드가 이 이름으로 로봇을 찾음. (재부팅·재설치해도 같은 이름)
- **센서**: `door-sensor-01`, `ambient-sensor-01`처럼 **일관된 이름**만 주면 됨. "이 센서가 누구 집이냐"는 백엔드가 설정표에서 연결하니, 로봇/IoT 팀은 이름만 고정하면 끝.

> 왜 이름표랑 별도 번호(UUID)를 같이 쓰냐면 — 이름표(`robot-01`)는 사람이 부르기 쉬운 별명, 백엔드 내부 UUID는 절대 안 바뀌는 주민번호. 이름표는 바꿔도 그 로봇(레코드)은 그대로예요.

## 7. 귀가 이야기 전체 흐름 (한눈에)

```
문센서: 문 열렸어요(DOOR_OPENED) ──▶ 백엔드: 귀가 작업 3번 생성
백엔드: 3번, 현관으로 가(NAVIGATE ENTRANCE) ──▶ 로봇
로봇: 3번 도착했어요(NAVIGATION_RESULT, scenarioId=3) ──▶ 백엔드
백엔드: 3번, "어서오세요" 말해(SPEAK) ──▶ 로봇
        ...시니어와 대화 (음성 담당 파트)...
백엔드: 3번, 제자리로 돌아가(NAVIGATE DEFAULT) ──▶ 로봇
로봇: 3번 도착했어요(NAVIGATION_RESULT, scenarioId=3) ──▶ 백엔드: 완료!
```

작업번호 3번이 편지마다 계속 따라다니는 게 보이죠? 이게 4장에서 강조한 echo의 이유입니다.

## 8. 로봇/IoT 팀에게 물어볼 것 (핵심만)

정밀 계약서 8장에 전체 체크리스트가 있고, 그중 **꼭 확정해야 할 3개**만 추리면:

1. 결과 답장에 **`scenarioId`를 그대로 돌려줄 수 있나요?** (제일 중요)
2. 편지 종류(`type`) 이름이 우리 목록과 **똑같나요?** (다르면 실제 이름 알려주기)
3. **QoS 1 / retain=false / 시간대 붙은 시각** 규칙 지킬 수 있나요?

나머지(payload 키 이름들)는 다르면 알려만 주면 우리 쪽 한 파일만 고치면 됩니다.

## 9. 이 약속이 바뀌면?

payload 키·이름은 당시 백엔드 가정값이었습니다. 이 내용은 설명 기록으로만 참고하고, 변경은 [`scenario-contract-v1.md`](./scenario-contract-v1.md)부터 반영합니다.
