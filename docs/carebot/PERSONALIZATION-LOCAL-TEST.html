01이 문서가 다루는 것 / 다루지 않는 것

다른 팀원이 로봇으로 주행을 테스트하는 동안, 우리는 “개인화된 대화가 실제로 이루어지는가”만 분리해서 검증한다.

다룬다 (이 문서의 범위)다루지 않는다
노트북 마이크·스피커로 ai_chat 단독 구동
STT → LangGraph → Gemini → TTS 왕복
어르신 발화의 사실 추출 · 기억 저장
다음 턴에서의 회상(개인화) 확인
보호자 화면·DB에서의 증거 확인 		Nav2 주행 · 좌표 · 사람 접근 (다른 팀원 담당)
MQTT 시나리오 트리거 (현관·복약·온습도)
웨이크워드 후 “이동 중 침묵”
젯슨 실기 오디오 특성 (에코·빔포밍)
주의 위 항목은 §14에서 “시연장 흐름”으로만 기술
⚠ 배포 EC2에 붙는다는 것의 의미

이 가이드는 BACKEND_BASE_URL=https://i15e102.p.ssafy.io/ 로 실제 배포 백엔드·실제 Postgres에 쓴다. 테스트 발화가 그대로 시연용 데이터에 섞인다. 반드시 테스트 전용 어르신 UUID로 SENIOR_ID를 잡고, 시연 대상 어르신(김순자 등)의 UUID를 쓰지 않는다. 어떤 UUID가 EC2에 살아 있는지는 실행 전 팀에 확인한다 (필드테스트 문서 기준 점검용 99999999-0000-4000-8000-000000000001).

아래가 “노트북 · 로봇 없음 · 배포 EC2 연결 · 개인화 반복 테스트” 조합의 최소 세트다.

BACKEND_TIMEOUT_SECONDS=3.0          # 기본 1.5는 로컬망→EC2에서 자주 타임아웃

# ── 오디오 ──────────────────────────────────────────────────
AUDIO_MODE=laptop
AUDIO_INPUT_DEVICE=
AUDIO_OUTPUT_DEVICE=

AUDIO_MAX_SECONDS=15

# ── 웨이크워드: 반복 테스트는 0, 시연 리허설은 1 ─────────────
WAKEWORD_ENABLED=0
WAKEWORD_MODEL_PATH=models/bomiya.onnx

# ── 대화 런타임 (그래프 경로 고정) ──────────────────────────

EXTRACTION_ENABLED=true           # 개인화 검증의 본체. 꺼지면 기억이 영원히 안 는다
T3_CONSENT_ENABLED=true
LOCALSTORE_DIR=var/localstore

# ── 로봇 없는 환경에서 반드시 꺼두는 것들 ───────────────────
MQTT_ENABLED=false                # 브로커 없으면 무한 재연결 로그로 화면이 덮인다
WAKE_MOVEMENT_WAIT_ENABLED=false  # true 면 매 호출마다 도착신호 45초를 그냥 날린다
SEARCH_SIGNAL_ENABLED=0
BEAM_FIX_ENABLED=0
DB_CONNECTION_MODE=direct               # 의료 조회 안 쓸 거면 그대로 둔다
값잘못 두면결과
SENIOR_ID임의값그 값으로 상태가 쌓이고, 나중에 바꾸는 순간 그동안의 기억이 전부 사라진 것처럼 보인다. EC2에 없는 UUID면 context 조회가 계속 빈 값이다.
BACKEND_SHARED_SECRET비움백엔드에 시크릿이 걸려 있으면 401. context는 조용히 로컬 캐시로 폴백하고, 대화 이벤트는 버려진다 → messageId가 없어 추출 큐에도 안 들어간다. “대화는 되는데 아무것도 저장 안 됨” 증상의 1순위 원인.
USE_GRAPH_RUNTIMEfalse게이트·트리아지·침묵 사다리·개인화가 통째로 빠진 구 파이프라인(STT→LLM→TTS)으로 돈다.
EXTRACTION_ENABLEDfalse큐잉도 flush도 안 한다. 대화는 저장되지만 memory는 한 줄도 안 생긴다.
MQTT_ENABLEDtrue브로커 없으면 재연결 로그 폭주. 켜도 START_CONVERSATION이 안 오면 의미 없다.

06이론: 말 한마디가 저장되는 경로

어르신이 한 번 말했을 때 LangGraph가 지나는 노드 순서. 순서 자체가 설계 결정이라 외워두면 디버깅이 빨라진다.

#노드하는 일
1note_interaction상호작용 시각 기록. “기억하지 마 / 잊어줘”를 분류보다 먼저 처리한다(프라이버시 우선).
2route_interaction“응”, “네” 같은 맞장구뿐이면 응답 없이 턴 종료.
3safety_triageT1(응급) 판정 시 context 조회와 LLM을 통째로 건너뛰고 확인·에스컬레이션으로 간다. 안전 설계.
4classify_intent로컬 규칙만. 네트워크 없음. context보다 먼저 도는 이유는 정보 질문일 때만 문서를 요청하기 위해서다.
5context_read턴 중 유일한 백엔드 동기 읽기. ↓아래 표 참조
6handle_*의도별 핸들러 7종 중 하나. 생성 LLM 호출은 여기 1회뿐.
7response_shaper모든 발화가 예외 없이 통과하는 문장 정제.
8emit스피커로 넘기고 즉시 반환. 일부러 저장보다 앞이라 HTTP가 말을 지연시키지 않는다.
9memory_write대화 이벤트 2건 전송 + last_spoke_at 기록 + 추출 큐 적재. 여기서 LLM은 안 돈다.

턴 중 오가는 HTTP

호출보내는 것 → 받는 것
POST /api/v1/seniors/{seniorId}/conversation-context → query, conversationId, memoryTopK, includeDocuments
← profile, todayState, recentMessages[], conversationSummary, relevantSummaries[], memories[], careRecords[], documents[], availability{}, retrieval{}
중요 이 호출은 절대 예외를 던지지 않는다. 실패하면 조용히 로컬 캐시로 내려간다 → 로그로만 구분 가능.
POST /api/v1/robot/conversation-events ×2 → seniorId, conversationId, role(SENIOR|ROBOT), content, occurredAt, triggerType
← conversationId, messageId, sequenceNo
어르신 행 먼저, 로봇 행 나중. 재시도 없음(max_attempts=1), 실패해도 대화는 계속된다.

어디에 무엇이 쓰이나

로봇 로컬 SQLite (var/localstore/)EC2 PostgreSQL
runtime_state — last_spoke_at, conversation_id
extraction_job — 추출 대기 큐 (발화 원문 + 직전 로봇 발화)
context_cache — 마지막 성공 context
fact_cancel_request — “잊어줘” 큐
emotional_signal, speech_proposal, consent_request, cached_audio
LangGraph checkpoint (thread_id = SENIOR_ID)
별도 파일 outbox.sqlite — 보호자 알림 큐 (synchronous=FULL) 		conversation / conversation_message — 대화 이벤트로 즉시
fact_candidate — 추출 틱이 제출
memory — 백엔드가 자동 확정 시 생성
care_record — 건강·일정 계열 확정 시
주의 로봇은 memory·care_record를 직접 쓰지 않는다. 항상 백엔드가 판단해서 만든다.

07발화 유형별 저장 결과표

“지금 어떤 말을 하면 어떻게 저장되는가” — 이 표가 이 문서의 핵심이다. 맨 오른쪽 “웹 화면” 열이 실제로 눈으로 볼 수 있는 범위이고, 이건 저장 여부와 다르다.

이렇게 말하면로봇 분류백엔드 매핑최종 상태웹 화면확인 방법 / 이유
“손자가 주말마다 놀러 와요” FAMILY MEMORY / PERSONAL_RELATIONSHIP 자동 확정
MATERIALIZED		 안 보임 EC2 memory 행은 생긴다. 그러나 visibility=PRIVATE 이고 프론트는 SHARED_WITH_*만 그린다 → DB SQL + 다음 턴 회상으로만 확인
“제가 화분 가꾸는 걸 좋아해요” HOBBY MEMORY / HOBBY 자동 확정 안 보임 동일. 다만 다음 턴 회상 테스트에는 가장 확실한 문장
“아침엔 늘 산책을 해요” DAILY_LIFE MEMORY / DAILY_ROUTINE 자동 확정 안 보임 동일
“요즘 무릎이 시큰거려요” HEALTH CARE_RECORD / HEALTH_CONDITION (민감) 확인 대기
NEEDS_CONFIRMATION		 반쯤 보임 /confirmation-requests 에 카드는 뜬다. 단 민감정보 마스킹(SAFE_VALUE_KEYS.HEALTH)이 content를 지워서 발화 내용이 안 보이고 일반 제목만 뜬다. 승인하면 목록에서 사라지고 어느 화면에도 안 남는다
“다음 주 화요일에 병원 가요” APPOINTMENT CARE_RECORD / APPOINTMENT 자동 확정 보인다 ★ /schedules 에 제목·시간·장소가 그대로 뜬다. 날짜 필터가 없어 미래 일정도 나온다. /dashboard의 todaySchedules는 오늘 것만이라 안 뜬다. startsAt 파싱 실패 시 MEMORY/OTHER로 강등되어 화면에서 사라진다
“방금 그건 기억하지 마” — 취소 큐 → /fact-candidates/cancel 삭제/취소 안 보임 취소 대상은 아직 확정 안 된 후보뿐이다. 기억·일정은 이미 MATERIALIZED라 이 경로로 못 지운다 → 실제로 취소되는 건 대기 중인 건강 후보뿐(카드가 사라지는 것으로 확인)
“가슴이 답답하고 숨이 안 쉬어져요” T1 응급 CARE_RECORD / GUARDIAN_ALERT 추출 제외 보인다 ★ /dashboard 안전 알림 카드 + 20초 긴급 토스트. 로봇 outbox가 /robot/guardian-alerts를 실제로 보내야 뜬다. 동의 여부와 무관하게 T1은 항상 나간다
✕ 결론: 화면으로 데모 가능한 건 7개 중 2개다

확실히 보이는 것 = 일정(/schedules)과 T1 응급(/dashboard) 둘뿐이다.
기억 3종(가족·취미·일상)은 구조적으로 화면에 못 뜬다 — 버그가 아니라 설계다. 자세한 이유는 §09.
따라서 “개인화가 된다”를 보여주는 최선의 방법은 화면이 아니라 로봇이 다음 턴에 그 내용을 언급하는 것이고, 화면 증거가 꼭 필요하면 일정 발화(“다음 주 화요일에 병원 가요”)를 쓰는 게 가장 깔끔하다.

추출 큐에 안 들어가는 7가지 (이거 몰라서 “저장이 안 된다”고 오진한다)

  1. EXTRACTION_ENABLED(env) 또는 코드 상수 중 하나라도 꺼짐
  2. 트리거가 어르신 발화가 아님 (능동 발화·백엔드 명령 턴)
  3. 안전등급 T1
  4. 의도가 onboarding 또는 clarification
  5. 발화가 6자 미만 — “네”, “좋아요”는 절대 안 들어간다
  6. 해당 대화가 봉인(sealed)됨
  7. messageId가 없음 — 즉 conversation-events 전송이 실패했다는 뜻. 401의 2차 증상

회상 확인의 요령

회상은 “똑같은 단어로 물어보기”보다 비슷한 주제를 다시 꺼내기가 잘 걸린다. 의미검색이 꺼진 기본 상태에서는 키워드 랭킹이라 기억에 들어간 명사(화분·손자·무릎)를 한 번 써주면 확실히 뜬다.

같지 않으면 선택지는 둘뿐이다 — (a) 배포 DB에서 user_type='SENIOR'인 행이 테스트 어르신 하나만 남도록 정리하거나, (b) 화면 검증을 포기하고 DB SQL + 다음 턴 회상으로만 판정한다.

14합격 기준 체크리스트

0단계 — 시작 전 (여기서 틀리면 나머지가 전부 무의미하다)

  • /api/v1/guardian/dashboard의 elder.id = .env의 SENIOR_ID
  • VITE_USE_MOCK_API=false · VITE_GUARDIAN_API_AUTH_READY=true 둘 다 설정
  • 시작 로그에 AUTH FAILURE가 없다

저장 층 (로그·DB)

  • 매 턴 retrieval source=backend (cache 아님)
  • 한 턴 후 EC2 conversation_message에 SENIOR/ROBOT 2행이 생긴다
  • 추출 flush 후 fact_candidate에 행이 생긴다
  • 가족/취미/일상 발화는 memory로 자동 확정된다 (SQL ③)
  • “기억하지 마”로 대기 중 후보가 취소된다

화면 층 (배포 서버 반영 확인)

  • /schedules 에 대화로 만든 일정 카드가 뜬다 ← 웹 화면 증거의 본체
  • 건강 발화가 /confirmation-requests 에 카드로 뜬다 (내용 마스킹은 정상)
  • T1 발화 시 /dashboard 안전 알림 + 긴급 토스트가 뜬다
  • 기억 3종은 화면에 안 뜨는 것이 정상 — 체크 항목이 아니다

개인화 층 (최종 판정)

  • 다음 턴에서 로봇이 저장된 내용을 스스로 언급한다 ← 이것이 “개인화가 된다”의 유일한 증거
  • 턴 지연이 체감상 3~5초 이내다 (turn latency 로그로 확인)
  • 같은 SENIOR_ID로 재시작해도 이전 기억이 이어진다 (checkpoint + EC2 memory)

15실제 시연장 흐름 — 무엇이 달라지나

로컬 검증에서 통과한 것은 대화·기억 층뿐이다. 시연장에서는 그 위에 트리거 층과 이동 층이 얹힌다.

✕ 시연장에서 우리 쪽이 가장 잘 깨지는 지점 3가지

① START_CONVERSATION → CONVERSATION_STARTED 는 10초 안이다. 문서엔 60초로 적혀 있지만 실제 코드는 10초. 넘기면 시나리오가 실패로 종결된다.
② 실패 결과 하나가 로봇을 잠근다. COMPLETED가 아닌 종결은 로봇을 SAFE_STOP으로 만들고 자동 복구 경로가 없다(재시작 무효). 리허설 사이마다 scripts/dev/reset-demo.sql을 돌린다.
③ 마이크는 한 스레드만 쥔다. 웨이크워드 대기 중 START_CONVERSATION으로 대화를 시작하는 경로(wake.interrupt_check)는 실기 미검증이다. 현관 인사 시나리오로 “보미야 없이 대화가 시작되는지”를 반드시 실측한다.

시연장 당일 순서 (우리 담당 부분)

  1. 젯슨에서 python -c "import sounddevice as sd; print(sd.query_devices())" → .env의 오디오 인덱스 갱신
  2. .env CRLF 확인 (dos2unix) — API 키가 조용히 실패한다
  3. ai_chat 테스트·단독 실행 시 env -u PYTHONPATH, 로봇 구동 시엔 유지
  4. MQTT 연결 로그 확인 → START_CONVERSATION 수신 여부 확인
  5. 현관 인사 1회 리허설 (= 마이크 인터럽트 실측)
  6. 리허설 끝날 때마다 reset-demo.sql
  7. 본 대화에서 개인화 문장이 실제로 나오는지 최종 확인 — 시연 전날까지 대본 A로 기억을 미리 심어둔다
✓ 시연 전날 해두면 좋은 것

시연에 쓸 어르신 계정으로 대본 A를 미리 3~4개 심어둔다. 추출 틱이 10분 주기라 당일 현장에서 말한 내용이 그날 대화에 반영될 가능성은 낮다. 개인화는 미리 쌓인 기억으로 보여주는 것이 안전하다.

16함정과 트러블슈팅

증상진짜 원인조치
대화는 잘 되는데 DB에 아무것도 안 쌓인다BACKEND_SHARED_SECRET 401로그에서 AUTH FAILURE 검색. 시크릿 재확인
기억을 하나도 못 불러온다SENIOR_ID가 EC2에 없는 UUIDretrieval ... hits=0이 계속되면 UUID부터 의심
10분을 기다려도 memory가 안 생긴다발화 6자 미만 / T1 / messageId 없음§07의 7가지 스킵 조건을 순서대로 대조
일정(병원 예약)만 추출이 안 된다profile.timeZone 없음flush 로그의 timeZone 경고 확인. 대화 한 턴 성공시켜 캐시 채우기
화면이 전부 비어 있다 / 다른 어르신이 보인다어르신 선택이 LIMIT 1이다. 인증도 선택 UI도 없다dashboard.elder.id와 SENIOR_ID 대조. 다르면 화면 검증 불가 → 배포 DB의 SENIOR 행 정리 또는 DB/회상 검증으로 전환
프론트에 기억이 안 보인다정상. 새 기억은 PRIVATE이고 승격 경로가 없다DB SQL이나 다음 턴 회상으로 확인. 화면 증거가 필요하면 일정 발화(대본 B)
일정을 말했는데 /schedules에 없다startsAt 파싱 실패 → MEMORY/OTHER 강등SQL ③에 OTHER로 들어갔는지 확인. 날짜·시각을 또렷하게(“다음 주 화요일 오전 열 시”) 다시 말한다
확인 요청 카드에 내용이 안 보인다정상. 민감정보 마스킹이 content를 제거발화 원문은 DB fact_candidate.proposed_value로 확인
승인했더니 어디에도 안 보인다정상. 승인된 건강 기록을 조회하는 화면·API가 없다DB care_record로 확인. 승인 전에 스크린샷을 남긴다
프론트 데이터가 전부 그럴듯한 가짜다두 Vite 플래그 미설정VITE_USE_MOCK_API=false + VITE_GUARDIAN_API_AUTH_READY=true
매 턴 응답이 느리다 / 캐시로 떨어진다BACKEND_TIMEOUT_SECONDS=1.5로컬망→EC2는 3.0으로 올린다
로봇이 자기 목소리에 반응한다에코 임계치 미실측헤드셋 사용. ECHO_GUARD_SEC·ECHO_VAD_THRESHOLD_MULTIPLIER는 추정치이며 실측 전 능동 발화 테스트 금지
재연결 로그가 화면을 덮는다MQTT_ENABLED=true인데 브로커 없음로컬 테스트에서는 false
파이썬 테스트가 죽는다ROS의 lark/numpy 충돌env -u PYTHONPATH 로 실행 (단, 로봇 구동 시엔 PYTHONPATH 유지)
SENIOR_ID를 바꿨더니 기억이 사라졌다정상. checkpoint thread_id이자 모든 저장 키테스트 중에는 절대 바꾸지 않는다
