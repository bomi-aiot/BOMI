# 착수 전 브랜치 점검 (읽기 전용)

**이 스킬이 끝날 때까지 파일을 하나도 고치지 않는다.** 목적은 단 하나 —
*이미 끝난 일을 다시 계획하는 것*을 막는 것이다.

## 왜 이게 첫 턴이어야 하는가

2026-08 세션 두 개가 정확히 이 이유로 "부분 달성"으로 끝났다. 티켓 230·218과
정서 핸들러가 **이미 머지되어 있었는데** 아닌 것처럼 계획하고 티켓을 등록했다.
사용자가 "꼬일거같음"으로 중단시켰고 253 구현은 폐기됐다.

읽기 전용 상태 보고는 1분이 든다. 잘못된 계획 패스 하나는 세션 하나를 태운다.

## 이 저장소의 함정 — 라인이 네 개다

```text
main
├── ai-main      ← ai-develop      ← S15P11E102-<n>-ai-<슬러그>
├── be-main      ← be-develop      ← S15P11E102-<n>-be-<슬러그>
├── fe-main      ← fe-develop      ← S15P11E102-<n>-fe-<슬러그>
└── robot-main   ← robot-develop   ← robot/feat/S15P11E102-<n>-<slug>
```

**한 라인을 체크아웃하면 다른 라인의 소스는 untracked 로 뜬다.** 예를 들어 AI
라인에서는 `backend/src` 에 자바 파일이 거의 없다 — 삭제된 것이 아니라 그 라인에
없는 것이다. 이걸 "구현이 안 되어 있다"로 착각하면 결론 전체가 틀어진다.

`CONTRIBUTING.md` 는 `feat/*` + 단일 `develop` 을 말하지만 **실제 관행과 다르다.**
실제 브랜치를 믿는다.

## 절차

```bash
git fetch --all --prune

git rev-parse --abbrev-ref HEAD          # 현재 브랜치
git status -sb                            # ahead/behind, 작업트리 상태
git worktree list                         # 열려 있는 worktree
git branch -r | grep -E 'develop|main$'   # 통합 라인
```

티켓마다 이미 머지됐는지 확인한다. **커밋 검색과 코드 검색을 둘 다 한다** —
커밋이 없어도 기능이 다른 티켓에 얹혀 들어간 경우가 있다.

```bash
git log --oneline --all --grep="S15P11E102-<번호>"
git branch -a | grep "<번호>"
# 그리고 그 기능의 식별자를 코드에서 직접 찾는다 (Grep)
```

## 출력 — 표만 낸다

| 티켓 | 상태 | 근거 | 대상 라인 | 다음 행동 |
| --- | --- | --- | --- | --- |
| -252 | 미착수 | 브랜치만 있고 커밋 0 | ai | 착수 가능 |
| -218 | **머지됨** | `5294522` → be-develop | be | 계획 금지 |

그리고 세 문장으로 끝낸다.

1. 지금 어느 라인에 서 있는가
2. 사용자가 말한 티켓 중 **이미 끝난 것**은 무엇인가
3. 라인이 어긋나는 티켓은 무엇인가 (→ 아래)

## 라인이 어긋나면 — 고치지 말고 티켓만 남긴다

대상 파일이 현재 브랜치 라인 소속이 아니면 **구현을 시작하지 않는다.** 원인·설계·
완료 조건을 정리해 두고, 사용자가 올바른 라인으로 옮긴 뒤 진행하게 한다.

2026-08-02 에 BE 브랜치에서 `robot/ai_chat/`(AI 전용)을 고치려 했고, 그 시점에
해당 트리의 `.py` 가 작업 트리에서 사라져 있었다. 유실은 아니었지만 사용자의
경계가 옳았다.

## 안티패턴

- 이 점검을 건너뛰고 바로 구현에 들어간다
- 세션 앞부분에서 본 브랜치 상태를 기억으로 재사용한다 (그 사이 머지가 들어온다)
- `git fetch` 없이 `git branch -r` 만 본다
- 커밋 검색만 하고 코드 검색은 생략한다
- 표 대신 산문으로 길게 설명한다 — 사용자는 판단 근거만 필요하다
