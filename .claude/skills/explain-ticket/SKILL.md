# 티켓 설명 (2패스)

머지가 끝난 변경을, 그 변경을 직접 하지 않은 사람이 이해할 수 있게 설명한다.
독자는 이 저장소의 팀원이고, **파이썬/LangChain/RAG를 빠르게 읽지 못한다**
(루트 `CLAUDE.md` §2). 그래서 코드부터 들이밀면 실패한다.

핵심 원칙 하나: **같은 내용을 두 번 설명한다.** 처음엔 그림을 그려주고,
두 번째엔 그 그림 위에 코드를 얹는다. 두 설명의 순서와 소제목은 일치시킨다.
그래야 독자가 "아까 그 이야기가 이 코드구나"로 연결한다.

---

## 0단계 — 재료 수집

설명을 시작하기 전에 근거를 모은다. 이 저장소에는 함정이 하나 있다:
**Jira 티켓 본문이 비어 있는 경우가 많고, 커밋 메시지도 제목 한 줄뿐이다.**
그래서 "왜"는 대개 **적혀 있지 않고 재구성해야 한다.**

```bash
# 티켓 번호로 커밋 찾기
git log --all --oneline --grep="S15P11E102-183"

# 무슨 파일이 얼마나 바뀌었나 (전체 diff 보기 전에 항상 이것부터)
git show --stat <sha>

# 브랜치 이름 훑기 — 커밋 없이 브랜치만 남은 티켓은 "부모/에픽"이다.
# 이 저장소의 브랜치 이름은 길고 서술적이라, 이름 자체가 사실상 티켓 본문이다.
git branch -a
```

Jira는 `getJiraIssue`로 조회할 수 있다(cloudId: ssafy.atlassian.net).
`description`이 `null`이면 거기서 얻을 게 없다는 사실 자체를 사용자에게 알려준다 —
"왜"를 추론으로 채운다는 걸 미리 밝혀야 신뢰가 유지된다.

**재료 우선순위**

| 순위 | 재료 | 무엇을 알려주나 |
| --- | --- | --- |
| 1 | **테스트 파일** | 사실상 스펙 문서. "이 티켓이 지키기로 한 약속"이 여기 있다 |
| 2 | AS-IS 코드 (`git show <sha>^:<path>`) | 뭐가 불편했는지는 옛 코드를 봐야 안다 |
| 3 | 루트 `CLAUDE.md`의 해당 § | 설계 규칙의 근거. 인용하면 설득력이 붙는다 |
| 4 | 브랜치 이름 / 커밋 제목 | 목적의 힌트 |
| 5 | 앞뒤 티켓 | 이 티켓이 무엇을 준비했고 무엇을 이어받았나 |

## 1패스 — 쉽게

목표: **코드를 한 줄도 안 읽어도 무슨 일이 있었는지 이해되게.**

### 구성

```markdown
# 티켓 <번호> — <제목>

## 한 문장으로
<비유 한 개>. <새 기능인지 정리인지 같은 성격 한 마디>

## 이 티켓 전에 뭐가 불편했나
### 불편 1 — <증상을 제목으로>
<왜 문제인지. 가능하면 최종 사용자에게 어떤 장면으로 나타나는지까지>
### 불편 2 — ...

## 그래서 뭘 했나
### ① <한 일>
### ② <한 일>

## 결과적으로 뭐가 좋아졌나
- 항목 나열

## 이 티켓이 남긴 것
- 잔해/미완성 → 어느 티켓이 이어받는지
```

### 규칙

- **비유로 연다.** "이사와 정리다", "열쇠를 한 곳에 모았다", "출발 전 점검".
  비유는 티켓 성격을 한 방에 잡아주고, 2패스에서 코드를 붙일 못이 된다.
- **코드는 넣지 않는다.** 꼭 필요하면 3줄 이하, 또는 실행 명령 한 줄 정도.
- **전문용어를 쓰지 않는다.** dataclass, 의존성 주입, lazy import, E402, 체크포인터 —
  전부 2패스로 미룬다. 1패스에서 불가피하면 그 자리에서 한 문장으로 푼다.
- **불편은 코드가 아니라 증상으로 쓴다.**
  나쁨: "`os.getenv()`가 각 모듈에 흩어져 있었다"
  좋음: "현관 열쇠를 화분 밑에, 자동차 열쇠를 신발장에 각각 숨겨둔 집.
  어디 뭐가 있는지 아무도 전체를 모른다"
- **가능하면 어르신 관점까지 내려간다.** 이 제품은 노인 돌봄 로봇이다.
  "설정 검증이 없었다"보다 "어르신이 말을 걸었는데 로봇이 아무 대답도 안 한다"가
  왜 고쳐야 하는지를 훨씬 잘 전달한다.
- **표를 쓴다.** 조건별 동작, 전후 비교는 산문보다 표가 빠르다.

## 2패스 — 코드로

1패스가 끝나면 **사용자가 넘어가자고 하기 전에 바로 이어서** 2패스를 낸다.

목표: **코드 블록만 따로 떼어 봐도 이해되게.**

### 구성

1패스의 소제목을 **그대로 다시 쓴다.** 같은 순서, 같은 이름.
각 항목 밑에 `### AS-IS` → `### TO-BE` 코드를 붙인다.

```markdown
# 티켓 <번호> — 2패스: 코드로 보기

`<sha>` · <N>파일 +<추가>/-<삭제> · <성격 한 마디>

## 불편 1 — <1패스와 똑같은 제목>
### AS-IS
<주석 달린 코드>
### TO-BE
<주석 달린 코드>

## 불편 2 — ...

## 테스트로 못박은 계약
<테스트 코드 + 각 테스트가 무엇을 보증하는지 주석>

## 이 티켓이 남긴 것
<diff 하단의 잔해를 주석과 함께>
```

### 규칙 — 주석이 이 패스의 본체다

**모든 코드 블록에 줄마다 주석을 단다.** 본문 산문과 내용이 중복돼도 좋다.
독자가 코드 블록만 스크롤해도 따라올 수 있어야 한다.

파일 트리는 **줄마다 역할 한 문장**:

```text
robot/ai_chat/src/bomi_ai_chat/   # ← 한 겹 더 감쌌다. 최상위 패키지 이름이
                                  #    "bomi_ai_chat" 하나뿐 → 남의 패키지와 안 겹친다
├── __init__.py                   #   "이 폴더는 패키지다" 표식 + __version__ 보관
├── config.py                     #   ★ 이번 티켓의 핵심. 환경변수 22개를 모은 곳 (신설)
└── llm/                          #   client.py(Gemini) + router.py(질문 판별)
```

설정 파일은 **각 줄이 왜 필요한지**:

```toml
[project.scripts]                            # ← 신설 블록
bomi-ai-chat = "bomi_ai_chat.main:main"      # pip install 하면 명령어가 생긴다
                                             # 젯슨에서 systemd 가 부팅 시 이걸 실행
```

파이썬은 **무슨 일이 일어나는지 + 어디를 봐야 하는지**:

```python
def __init__(self, settings: Settings | None = None):
    #                ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    #   ★ 이 한 줄이 핵심.
    #   - 평소 호출부는 STTClient() 그대로 → 기존 코드 안 고쳐도 됨
    #   - 테스트는 STTClient(settings=가짜설정) → 환경변수 안 건드리고 값 주입
    #   이 기법 이름이 "의존성 주입(dependency injection)".
    settings = settings or get_settings()   # 안 넘겨주면 전역 설정을 알아서 가져옴
```

- **`★`로 핵심 줄을 짚는다.** 주석이 많아지면 어디가 중요한지 묻히기 때문이다.
- **전문용어는 여기서 처음 제대로 쓰되, 옆에 풀이를 붙인다.**
  "`frozen=True` = 한 번 만들면 수정 불가 → 실행 중 설정 바꿔치기를 구조적으로 차단"
- **AS-IS 코드에는 "이래서 문제"를 주석으로 적는다.** 옛 코드를 그냥 보여주기만 하면
  독자는 뭐가 잘못됐는지 모른다.
- **전체 diff를 붙이지 않는다.** 판단이 드러나는 지점만 고른다. rename만 잔뜩인
  커밋은 "대부분 파일 이동이라 실제 로직 변경은 적다"고 한 줄로 처리한다.
- **순서 비교표**를 쓰면 실행 흐름 변경이 잘 보인다.

  | | AS-IS | TO-BE |
  |---|---|---|
  | 1 | `.env` 로드 (임포트 사이) | 설정 로드 + **검증** |
  | 2 | **무거운 모델 로딩** | 설정 틀리면 → **여기서 종료** |

## 근거 표기 — 지어내지 않기

Jira에 본문이 없으니 목적의 상당 부분은 추론이다. **추론은 추론이라고 표시한다.**

- 문서·코드·테스트에 근거가 있으면 그대로 인용하고 출처를 밝힌다
  (`CLAUDE.md §7`, `test_package.py`, 커밋 제목).
- 근거 없이 diff에서 읽어낸 의도는 **`[추론]`**을 붙인다.
  예: "**진짜 목적** [추론]: 젯슨 배포 준비다. 근거 세 가지 — ①…②…③…"
- 추론에는 항상 근거를 같이 댄다. 근거를 못 대겠으면 그 추론은 빼는 게 낫다.

## 마무리 — 티켓을 사슬로 잇기

티켓 하나를 고립시켜 설명하면 "그래서 이게 왜 지금 필요했나"가 안 남는다.
매 티켓 끝에 두 방향을 적는다.

- **뒤로**: 이 티켓이 남긴 잔해·미완성이 어느 티켓으로 넘어가는가
  ("빈 파일 몇 개가 남았다 → 186에서 치운다", "5줄 껍데기 → 185에서 채운다")
- **앞으로**: 다음 티켓이 이 티켓의 무엇 위에 올라타는가
  ("클라이언트가 주입 가능해졌으니 이제 테스트를 자동화할 수 있다 → 181")

여러 티켓을 연속으로 설명할 때는 **처음에 전체 지도를 먼저 그린다.**
부모 티켓의 항목이 자식 티켓으로 어떻게 쪼개졌는지 표로 보여주면,
이후 티켓들이 왜 그 순서인지가 저절로 설명된다.

그리고 한 티켓이 끝나면 **다음으로 넘어갈지 물어본다.** 한 번에 몰아치지 않는다.

## 안티패턴

- 1패스에 코드 블록을 도배한다 (그럼 1패스가 존재할 이유가 없다)
- 2패스에서 주석 없는 코드를 붙인다 (그럼 diff를 그냥 보라고 하는 것과 같다)
- `git show`의 diff를 통째로 붙여넣는다
- 1패스와 2패스의 순서·소제목이 어긋난다
- 근거 없는 목적을 단정한다 (`[추론]` 없이 "이건 성능 때문이다")
- 티켓 하나만 보고 앞뒤 연결을 빼먹는다
- 사용자가 묻지도 않았는데 코드를 고치기 시작한다 — 이 스킬은 **설명 전용**이다
