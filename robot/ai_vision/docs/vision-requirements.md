# BOMI AI Vision 기능 요구사항

## 1. 문서 목적

이 문서는 BOMI 돌봄 로봇에서 사용하는 AI 비전 모듈의 기능 요구사항을 정의한다.

AI 비전 모듈은 카메라 영상을 분석해 다음 정보를 제공한다.

* 영상에 존재하는 사람의 수
* 보호대상자 추적 상태
* 보호대상자의 화면상 위치
* 보호대상자가 누워 있거나 쉬고 있을 가능성
* 로봇이 능동적으로 말을 걸어도 되는 상태인지 여부

이 문서는 AI 비전 모듈이 반드시 구현해야 하는 동작과 구현하지 않을 범위를 명확히 구분하기 위해 사용한다.

구현 결과가 이 문서와 다르다면 코드를 기준으로 **요구사항을 낮추지 않는다.** 요구사항 변경이 필요한 경우 변경 이유와 영향을 검토한 뒤 문서를 먼저 수정한다.

다만 **진척 기록은 요구사항 변경이 아니다.** 각 절에는 현재 구현 상태를 `구현됨` / `부분 구현` / `미착수` / `다른 형태로 대체됨` 중 하나로 표기하며, 표기를 갱신하는 것은 요구사항을 깎는 행위가 아니다. 표기가 없으면 미구현 요구사항이 현재 동작으로 오독되고, 실제로 그 오독이 `ARCHITECTURE.md`와 `docs/state-machine.md`로 전파된 적이 있다.

## 2. 프로젝트 배경

BOMI는 독거노인 또는 돌봄이 필요한 보호대상자를 지원하는 이동형 로봇이다.

로봇은 사용자를 따라다니며 대화하고, 일정 알림이나 개인화된 정보를 제공한다.

AI 비전 기능은 다음 두 가지 주요 목적을 가진다.

1. 로봇이 따라가야 할 보호대상자의 위치를 파악한다.
2. 보호대상자가 잠들었거나 쉬고 있을 가능성이 있을 때 로봇이 먼저 말을 걸지 않도록 한다.

AI 비전 모듈은 사람의 의료 상태를 진단하거나 로봇을 직접 제어하는 모듈이 아니다.

---

## 3. MVP 운영 전제

현재 MVP는 다음 환경을 전제로 한다.

### 3.1 보호대상자 수

* 정상 운영 환경에는 보호대상자 한 명만 존재한다.
* 영상에서 유효한 사람이 정확히 한 명 검출되면 해당 사람을 보호대상자로 간주한다.
* 보호대상자의 실제 신원을 별도로 확인하지 않는다.

### 3.2 카메라 환경

* 로봇에 장착된 단일 RGB 카메라를 기본 입력 장치로 사용한다.
* 카메라는 로봇의 전방 또는 보호대상자가 존재할 가능성이 높은 방향을 촬영한다.
* 카메라 영상은 일정한 프레임 단위로 AI 비전 모듈에 전달된다.
* 야간, 역광, 심한 가림, 화면 이탈 등의 상황에서는 판단이 불가능할 수 있다.

### 3.3 처리 장치

* 최종 실행 환경은 Jetson Orin Nano를 기준으로 한다.
* 초기 개발과 기능 검증은 일반 PC에서도 수행할 수 있어야 한다.
* 초기 구현은 Python과 Ultralytics 기반으로 진행할 수 있다.
* TensorRT 및 ROS2 최적화는 핵심 기능 검증 이후 적용한다.

## 4. 기능 범위

AI 비전 모듈의 MVP 기능은 다음과 같다.

### 4.1 사람 탐지

> **구현 상태: 다른 형태로 대체됨.** 별도의 탐지 단계는 런타임 경로에 없다. 파이프라인은 Ultralytics 통합 추적(`model.track`)을 한 번 호출해 탐지와 추적을 동시에 얻는다. `UltralyticsPersonDetector`는 정의만 남아 있고 인스턴스화되지 않는다(`adapters/detection.py`). 또 `PersonDetection`에는 클래스 ID 필드가 없다 — 어댑터가 사람 클래스만 남기고 걸러내므로 하류에서 다시 쓸 일이 없기 때문이다.

* 영상 프레임에서 사람 클래스를 탐지한다.
* YOLO 계열 객체 탐지 모델을 사용한다.
* 사람 이외의 객체는 보호대상자 판단에 사용하지 않는다.
* 모델 confidence가 설정된 기준보다 낮은 탐지는 유효한 사람 수에서 제외한다.
* 탐지 결과에는 최소한 다음 정보가 포함돼야 한다.

  * 바운딩 박스
  * confidence
  * 클래스 ID
  * 화면 중심 좌표

### 4.2 사람 추적

* ByteTrack을 이용해 연속된 프레임에서 동일한 사람의 Track ID를 유지한다.
* Track ID는 현재 영상 안에서 사람을 추적하기 위한 임시 식별자로만 사용한다.
* Track ID를 실제 사용자 신원으로 간주하지 않는다.
* 사람이 잠시 가려지거나 탐지가 누락돼도 설정된 허용 범위 안에서는 기존 추적 상태를 유지할 수 있다.
* 화면을 완전히 벗어나거나 장시간 탐지되지 않으면 추적 실패 상태로 전환한다.

### 4.3 보호대상자 선택

* 유효한 사람이 정확히 한 명이면 해당 사람을 현재 보호대상자로 간주한다.
* 두 명 이상이 검출되면 특정 사람을 보호대상자로 임의 선택하지 않는다.
* 가장 큰 바운딩 박스, 가장 높은 confidence 또는 기존 Track ID만으로 다중 인물 중 한 사람을 강제로 선택하지 않는다.
* 얼굴인식이나 Person Re-ID를 이용한 보호대상자 신원 확인은 MVP에서 수행하지 않는다.

> **명시적 예외 하나가 구현돼 있다.** `--select-primary-person`(기본 꺼짐)을 켜면 상태 머신에 넘기기 **전에** 후보를 한 명으로 줄인다(`primary_person.py`). 기준은 신뢰도가 아니라 화면 중앙 최근접이고, 동률이면 상자 높이, 그다음 Track ID다. 한 번 고른 대상은 화면에 남아 있는 동안 유지한다(히스테리시스). 조건을 통과한 후보가 없으면 원본 목록을 그대로 넘겨 위의 "임의 선택하지 않는다" 규칙이 살아난다. 이 예외는 구경꾼이 있는 사람 추종 시연이 성립하지 않아 도입했으며, **실기 launch와 시연 스크립트는 항상 켠다.** 요구사항으로 승격할지, 시연 전용 예외로 못박을지는 아직 결정되지 않았다.

### 4.4 사람 수 상태 판단

AI 비전 모듈은 유효한 사람 수와 이전 상태를 바탕으로 보호대상자 추적 상태를 결정한다.

필수 상태는 다음과 같다.

* `NOT_DETECTED`
* `TRACKING`
* `TEMPORARILY_LOST`
* `MULTIPLE_PENDING`
* `MULTIPLE_PERSONS`
* `SINGLE_RECOVERY`

상세한 상태 전환 규칙은 `docs/state-machine.md`에서 정의한다.

### 4.5 화면상 위치 계산

한 명의 보호대상자를 정상적으로 추적할 때 다음 정보를 계산한다.

* 바운딩 박스 좌표
* 바운딩 박스 중심 좌표
* 프레임 너비와 높이를 기준으로 정규화한 중심 좌표
* 보호대상자의 화면상 방향

화면상 방향은 최소한 다음 세 구역으로 구분할 수 있어야 한다.

* `LEFT`
* `CENTER`
* `RIGHT`

구역 경계는 설정값으로 관리한다.

> **구현 상태: 다른 형태로 대체됨.** 별도의 방향 enum은 만들지 않았다. 대신 정규화 가로 오프셋 `offset_x`와 수평 중앙 허용 범위(`--horizontal-dead-zone`, 코드 기본 0.15)로 같은 판정을 하고, 결과를 방향이 아니라 추종 희망 명령(`turn_left`/`turn_right`/`move_forward`/`stop`)으로 내보낸다. 구역 경계가 설정값이어야 한다는 요구는 충족된다. 이 절을 읽고 없는 enum을 새로 만들지 않는다.

AI 비전 모듈이 제공하는 위치는 카메라 화면 기준 방향이다. 실제 거리와 장애물은 LiDAR 또는 다른 센서가 담당한다.

### 4.6 다중 인물 처리

두 명 이상의 사람이 검출되는 상황은 정상 운영 조건에서 벗어난 예외 상황으로 처리한다.

필수 동작은 다음과 같다.

1. 한 프레임에서 두 명 이상이 검출됐다는 이유만으로 즉시 확정 상태로 전환하지 않는다.
2. 설정된 프레임 수 또는 시간 동안 다중 인물 검출이 지속되면 `MULTIPLE_PERSONS` 상태로 전환한다.
3. 다중 인물 상태에서는 보호대상자를 선택하지 않는다.
4. 다중 인물 상태에서는 능동 대화를 허용하지 않는다.
5. 주행 시스템이 사용할 수 있도록 이동 비허용 상태를 제공한다.
6. 다시 한 명만 검출되더라도 즉시 정상 추적으로 복귀하지 않는다.
7. 한 명 상태가 설정된 안정화 기간 동안 유지된 뒤 `TRACKING`으로 복귀한다.

AI 비전 모듈은 로봇의 모터를 직접 정지시키지 않는다. 상태 정보만 외부 시스템에 제공한다.

### 4.7 일시적 추적 실패 처리

사람이 순간적으로 탐지되지 않는 상황을 바로 영구적인 추적 실패로 처리하지 않는다.

다음 상황을 고려한다.

* 사람과 카메라 사이에 장애물이 잠시 지나감
* 프레임 일부에서 YOLO 탐지가 실패함
* 사람이 화면 가장자리로 이동함
* 조명 변화로 confidence가 일시적으로 낮아짐

설정된 허용시간 또는 허용 프레임 안에서는 `TEMPORARILY_LOST` 상태를 사용할 수 있다.

허용 범위를 초과하면 `NOT_DETECTED` 상태로 전환한다.

일시적 추적 실패 상태에서는 능동 대화를 허용하지 않는다.

## 5. 수면 및 상호작용 상태 추정

## 5.1 기능 목적

수면 관련 기능의 목적은 사용자가 잠들었거나 쉬고 있을 가능성이 있을 때 로봇이 능동적으로 말을 걸지 않도록 하는 것이다.

이 기능은 의료적인 수면 진단이 아니다.

다음과 같은 표현을 사용하지 않는다.

* 사용자가 실제로 수면 상태라고 확정함
* 수면 단계 또는 수면의 질을 판단함
* 의학적인 수면 장애를 진단함

기능 명칭과 결과는 수면 확정이 아니라 수면 가능성 또는 상호작용 가능 상태로 표현한다.

---

## 5.2 수면 상태 (미착수)

> **구현 상태: 미착수.** 아래 네 상태는 코드에 없다(`grep -rn "RESTING\|AWAKE\|SLEEPING" src tests scripts` → 0건). §5 전체와 §13.4가 여기에 해당하며, 자세·움직임 분석 방식이 결정되기 전까지 목표 상태로만 읽는다.

필수 상태는 다음과 같다.

* `UNKNOWN`
* `AWAKE`
* `RESTING`
* `SLEEPING_ESTIMATED`

### `UNKNOWN`

다음과 같이 판단에 필요한 정보가 부족한 상태다.

* 사람이 검출되지 않음
* 두 명 이상이 검출됨
* 신체가 심하게 가려짐
* 자세를 판단할 수 없음
* 영상 입력이 유효하지 않음
* 내부 분석 오류 발생

`UNKNOWN` 상태에서는 능동 대화를 허용하지 않는다.

### `AWAKE`

보호대상자가 서 있거나 앉아 있고, 정상적인 움직임이 관찰되는 상태다.

`AWAKE` 상태는 능동 대화 허용 후보가 될 수 있다.

단, 사람 추적 상태와 confidence 등 다른 조건도 함께 충족해야 한다.

### `RESTING`

보호대상자가 누워 있거나 장시간 편안한 자세를 유지하지만 실제 수면 여부는 확정할 수 없는 상태다.

`RESTING` 상태에서는 능동 대화를 허용하지 않는다.

### `SLEEPING_ESTIMATED`

보호대상자가 누운 상태를 일정 시간 유지하고 움직임이 매우 적어 수면 중일 가능성이 높다고 추정되는 상태다.

`SLEEPING_ESTIMATED` 상태에서는 능동 대화를 허용하지 않는다.

## 5.3 수면 및 휴식 상태 판단 입력

초기 MVP에서는 보호대상자의 자세와 시간에 따른 움직임 정보를 조합해
능동 대화를 제한할 필요가 있는지 판단한다.

필수적으로 검토할 정보는 다음과 같다.

* 보호대상자가 정상적으로 추적되고 있는지 여부
* 보호대상자가 서 있거나 앉아 있거나 누워 있는지에 대한 자세 정보
* 프레임 간 보호대상자의 움직임 크기
* 동일한 자세와 움직임 상태가 유지된 시간

각 정보는 단독으로 실제 수면을 확정하는 근거로 사용하지 않는다.

예를 들어 보호대상자가 누워 있다는 이유만으로 즉시
`SLEEPING_ESTIMATED` 상태로 전환하지 않는다.

자세와 움직임 정보를 계산하는 구체적인 기술은 실제 영상 테스트와
Jetson Orin Nano 성능 측정 이후 결정한다.

## 5.4 수면 및 휴식 상태 판단 방식 검토 후보

다음 방법은 현재 확정된 구현 요구사항이 아니며, 기술 검증을 위한 후보로 관리한다.

* 사람 바운딩 박스의 가로·세로 비율
* YOLO Pose를 이용한 신체 주요 지점 분석
* 바운딩 박스 중심점의 프레임 간 이동량
* 보호대상자 영역 내부의 프레임 차이
* Optical Flow를 이용한 움직임 분석
* 특정 공간이나 영역에 대한 ROI 활용
* 수면 또는 자세 분류 모델 활용

Codex는 활성 실행 계획에 명시되지 않은 후보 방법을 임의로 구현하지 않는다.

어떤 방법을 적용할지는 다음 기준을 비교한 뒤 결정한다.

* 실제 촬영 환경에서의 정확도
* 이불이나 가림 상황에 대한 안정성
* 카메라 각도에 대한 민감도
* Jetson Orin Nano에서의 처리속도
* 구현 및 테스트 기간
* 추가 데이터셋 필요 여부

## 5.5 누운 자세 판단

초기 구현에서는 다음 방법을 단계적으로 검토한다.

1. 바운딩 박스 가로·세로 비율
2. 보호대상자 바운딩 박스의 방향과 위치
3. YOLO Pose를 이용한 신체 주요 지점 분석
4. 침대 ROI와 자세 정보 결합

바운딩 박스 비율만으로 수면을 확정하지 않는다.

다음 상황에서는 비율 기반 판단이 잘못될 수 있다.

* 사람이 웅크리고 앉음
* 카메라 각도가 기울어짐
* 신체 일부가 이불에 가려짐
* 바운딩 박스가 신체 전체를 포함하지 못함
* 사람이 카메라를 향해 누움

따라서 누운 자세 결과에는 confidence 또는 판단 가능 여부를 함께 제공하는 것이 좋다.

## 5.6 움직임 판단

보호대상자의 움직임은 프레임 간 정보를 이용해 계산한다.

검토 가능한 입력은 다음과 같다.

* 바운딩 박스 중심점 이동 거리
* 바운딩 박스 크기 변화
* Pose keypoint 이동 거리
* 보호대상자 ROI 내부의 프레임 차이
* Optical Flow

초기 MVP에서는 계산 비용과 구현 난도를 고려해 단순한 방식부터 적용한다.

움직임 기준값은 카메라 해상도와 프레임 속도에 영향을 받으므로 설정값으로 관리한다.

## 5.7 능동 대화 허용 조건

능동 대화는 다음 조건을 모두 만족할 때만 허용한다.

1. 유효한 사람이 정확히 한 명이다.
2. 보호대상자 추적 상태가 `TRACKING`이다.
3. 수면 관련 상태가 `AWAKE`다.
4. 결과 confidence가 설정된 최소 기준 이상이다.
5. 영상이 설정된 최대 지연시간보다 오래되지 않았다.
6. 내부 처리 오류가 없다.

다음 상태에서는 능동 대화를 허용하지 않는다.

* `NOT_DETECTED`
* `TEMPORARILY_LOST`
* `MULTIPLE_PENDING`
* `MULTIPLE_PERSONS`
* `SINGLE_RECOVERY`
* `UNKNOWN`
* `RESTING`
* `SLEEPING_ESTIMATED`

능동 대화를 금지하는 것은 로봇의 모든 응답을 차단한다는 의미가 아니다.

사용자가 먼저 음성으로 로봇을 호출한 경우의 응답 정책은 대화 시스템에서 별도로 결정한다.

## 6. 입력 요구사항

> **구현 상태: 부분 구현.** 지원되는 입력은 **카메라 인덱스 하나**뿐이다(`--camera`, OpenCV `VideoCapture`). 로컬 영상 파일 경로도, ROS 2 이미지 Topic 구독도 없다. 다만 계층 규칙은 지켜져 있어 `OpenCVCamera`를 대체하는 어댑터 하나만 추가하면 나머지 로직은 그대로 재사용된다.
>
> 실기에서 반드시 함께 지정해야 하는 것이 하나 더 있다. **헤드리스(SSH) 환경에서는 `--no-window`가 필수**다 — 없으면 OpenCV Qt 플러그인 로딩에서 프로세스가 즉시 죽는다. 실기 launch는 헤드리스를 기본으로 본다.

AI 비전 모듈은 최소한 다음 입력 방식을 지원할 수 있도록 설계한다.

### 6.1 개발 단계

* 로컬 영상 파일
* USB 웹캠
* 노트북 내장 카메라

### 6.2 통합 단계

* ROS2 `sensor_msgs/Image`
* ROS2 `sensor_msgs/CompressedImage`는 필요 시 추가 검토

핵심 분석 로직은 입력 방식에 직접 의존하지 않아야 한다.

영상 파일, 웹캠, ROS2 입력은 각각 adapter 계층에서 처리한다.

## 7. 출력 요구사항

> **구현 상태: 다른 형태로 대체됨.** 이 절이 나열하는 항목 대부분은 외부로 나가지 않는다. **실제 외부 출력은 UDP JSON 4필드가 전부다.**
>
> ```json
> {"status":"tracking","command":"move_forward","track_id":7,"reason":"user_far_and_centered"}
> ```
>
> 프레임 정보(§7.1)와 위치값(§7.2의 좌표·정규화 좌표·바운딩 박스)은 **하나도 전송하지 않는다.** 거리 판단은 로봇 쪽 LiDAR가 담당하기로 경계를 그었기 때문이다. §7.3 중 실제로 나가는 것은 사람 추적 상태와 판단 이유뿐이며, 이유는 한국어 문장이 아니라 영문 스네이크 토큰이다.
>
> 수신측 계약을 만들 때는 이 절이 아니라 `src/bomi_vision/adapters/udp.py`와 `README.md`의 UDP 계약 표를 본다. 아래 §7.1~§7.4는 목표 형태로 남겨 둔다.

AI 비전 파이프라인의 최종 결과에는 최소한 다음 정보가 포함돼야 한다.

### 7.1 프레임 정보

* 처리 시각
* 원본 프레임 식별 정보 또는 시퀀스 번호
* 프레임 너비
* 프레임 높이
* 추론 처리시간

### 7.2 사람 정보

* 유효한 사람 수
* 보호대상자 Track ID
* 보호대상자 confidence
* 보호대상자 바운딩 박스
* 보호대상자 중심 좌표
* 정규화된 중심 좌표
* 화면상 방향

보호대상자를 선택할 수 없는 경우 Track ID와 위치 정보는 `None` 또는 명시적인 미지정 값으로 반환한다.

### 7.3 상태 정보

* 사람 추적 상태
* 수면 추정 상태
* 능동 대화 허용 여부
* 이동 허용 여부 또는 안전 상태
* 상태 판단 이유
* 전체 결과 confidence
* 오류 코드 또는 오류 메시지

### 7.4 결과 예시

> **주의: 아래 세 예시는 목표 형태이며 현재 전송되는 페이로드가 아니다.** 필드 이름이 실제 UDP 페이로드와 한 개도 일치하지 않는다. 이 JSON을 계약으로 믿고 수신측을 만들면 전부 어긋난다. 실제 페이로드는 §7 머리말의 4필드다.

정상 추적 상태:

```json
{
  "person_count": 1,
  "person_state": "TRACKING",
  "track_id": 7,
  "confidence": 0.91,
  "center_x_normalized": 0.54,
  "center_y_normalized": 0.62,
  "direction": "CENTER",
  "sleep_state": "AWAKE",
  "interaction_allowed": true,
  "movement_allowed": true,

}
```

다중 인물 상태:

```json
{

  "direction": null,
  "sleep_state": "UNKNOWN",
  "interaction_allowed": false,
  "movement_allowed": false,
  "reason": "두 명 이상의 사람이 지속적으로 검출되어 보호대상자를 특정할 수 없습니다."
}
```

수면 추정 상태:

```json

  "person_state": "TRACKING",
  "track_id": 4,
  "confidence": 0.83,
  "direction": "RIGHT",

```

## 9. 오류 및 예외 처리 요구사항

> **구현 상태: 부분 구현.** §9.4의 설정 검증은 argparse 타입 함수(`parse_confidence`, `parse_multiple_confirm_frames` 등)와 도메인 생성자가 시작 시점에 수행한다. 반면 **§9.2의 "연속 실패가 기준을 초과한 경우 안전 상태로 전환"은 구현되지 않았다** — 처리 루프는 `camera.read()`가 실패하면 예외를 올려 그대로 종료한다. 연속 실패 카운터도, 재시도도 없다. 다만 `udp_main`은 종료 경로에서 정지 패킷을 한 번 보내므로 로봇이 마지막 명령을 붙잡고 계속 움직이지는 않는다.

### 9.1 모델 로딩 실패

모델 파일이 없거나 로딩에 실패하면 명확한 오류를 발생시킨다.

실패한 상태에서 임의의 정상 결과를 생성하지 않는다.

### 9.2 영상 입력 실패

카메라 또는 영상 파일을 열 수 없으면 원인과 입력값을 포함한 오류를 반환한다.

실행 중 프레임 읽기에 실패하면 다음 중 적절한 처리를 수행한다.

* 영상 파일이 끝난 경우 정상 종료
* 카메라 프레임이 일시적으로 누락된 경우 재시도
* 연속 실패가 기준을 초과한 경우 안전 상태로 전환

### 9.3 추론 실패

특정 프레임의 추론에 실패하면 오류를 기록하고 해당 프레임 결과를 안전 상태로 반환한다.

권장 안전 결과:

* `person_state`: `NOT_DETECTED` 또는 별도 `ERROR`
* `sleep_state`: `UNKNOWN`
* `interaction_allowed`: `false`
* `movement_allowed`: `false`

### 9.4 잘못된 설정

다음과 같은 설정은 프로그램 시작 시 검증한다.

* confidence가 0.0 미만 또는 1.0 초과
* 확인 프레임 수가 1 미만
* 시간값이 음수
* ROI 좌표가 허용 범위를 벗어남
* 이미지 크기가 0 이하
* 존재하지 않는 모델 경로

## 10. 비기능 요구사항

### 10.1 가독성

* 모든 코드는 `docs/code-style.md`를 따른다.
* Python 파일, 클래스, 함수에는 한국어 docstring을 작성한다.
* 중요한 정책값과 상태 전환에는 한국어 설명을 작성한다.

### 10.2 테스트 가능성

* 상태 머신과 좌표 계산은 모델 없이 단위 테스트할 수 있어야 한다.
* YOLO와 ByteTrack은 adapter 또는 인터페이스 뒤에 분리한다.
* 카메라 입력 없이 저장 영상 또는 가짜 입력으로 파이프라인을 검증할 수 있어야 한다.

### 10.3 확장성

* YOLO 모델을 교체할 때 핵심 상태 로직을 수정하지 않아야 한다.
* 입력 방식을 웹캠에서 ROS2로 변경해도 핵심 분석 로직을 재사용할 수 있어야 한다.
* 수면 자세 분석 방식을 바운딩 박스에서 Pose 기반으로 교체할 수 있어야 한다.

### 10.4 성능

초기 기능 검증 단계에서는 정확성과 안정성을 우선한다.

이후 Jetson Orin Nano에서 다음 항목을 측정한다.

* 평균 FPS
* 프레임별 추론시간
* GPU 사용량
* GPU 메모리 사용량
* CPU 사용량
* 전체 파이프라인 지연시간

성능 기준은 실제 카메라와 통합 환경 테스트 후 확정한다. 위 항목을 측정하는 코드는 아직 없다.

> **실기에서 드러난 진짜 요구는 측정이 아니라 제약이었다.** 처리 루프에 프레임 레이트 상한이 없어 젯슨에서 전 코어를 90%까지 채웠고, 그 결과 Nav2의 20 Hz 제어 루프와 lifecycle·costmap 서비스 호출이 데드라인을 놓쳐 주행이 실패했다(2026-08-09 실기: amcl 활성화 실패, 경로 계획 실패). 대응은 문서가 아니라 실행 스크립트로 들어갔다 — `robot/scripts/run-homecoming-follow.sh`가 `taskset`으로 이 프로세스를 마지막 두 코어에 가두고 나머지를 Nav2에 남긴다.
>
> 따라서 **"Nav2의 실시간 제어 루프를 방해하지 않을 것"이 이 모듈의 실질적인 비기능 요구사항이다.** 프레임 레이트 상한이나 CPU 예산을 코드에 넣을지, 지금처럼 실행 계층에서 가둘지는 아직 결정되지 않았다.

### 10.5 개인정보 보호

* 영상 원본을 기본적으로 외부 서버에 전송하지 않는다.
* 디버그 영상 저장은 설정을 통해 활성화한 경우에만 수행한다.
* 저장 영상에는 보호대상자의 개인정보가 포함될 수 있음을 고려한다.
* 불필요한 얼굴 이미지와 장시간 영상을 저장하지 않는다.
* 얼굴인식용 생체정보를 수집하지 않는다.

## 11. MVP 제외 범위

다음 기능은 현재 MVP에서 구현하지 않는다.

* 얼굴인식
* 얼굴 등록
* Person Re-ID
* 다중 보호대상자 지원
* 방문자와 보호대상자 자동 구별
* 여러 카메라 사이의 동일 인물 추적
* 의료적 수면 진단
* 수면 단계 분석
* 호흡수 또는 심박수 측정
* 감정 인식
* 낙상 감지
* 클라우드 기반 실시간 영상 분석

다음 네 가지는 "안 만든다"가 아니라 **책임이 다른 모듈에 있다**는 뜻이다. 협업 경계이므로 제외 목록과 구분한다.

| 항목 | 소관 |
|---|---|
| 로봇 모터 직접 제어, 자율주행 경로 생성 | `robot/ros2_ws/src/core`(`person_follower`)와 Nav2 |
| LiDAR 기반 거리 계산 | `core` — 이 모듈이 위치값을 UDP로 보내지 않는 이유이기도 하다 |
| TTS 직접 실행 | `robot/ai_chat` |
| 대화 정책 직접 결정 | `robot/ai_chat`과 백엔드 |

향후 필요성이 확인되면 별도의 요구사항과 실행 계획을 작성한 뒤 추가한다.

## 12. 단계별 구현 우선순위

> **진척: 1~4단계 완료, 5~9단계 미착수.** 각 단계 제목 옆의 표기를 함께 읽는다. 1단계는 "완료"가 아니라 통합 추적으로 대체됐고, 4단계의 `LEFT`/`CENTER`/`RIGHT` 분류도 추종 명령으로 대체됐다(§4.5).

### 1단계: 사람 탐지 (다른 형태로 대체됨)

* YOLO 모델 로딩
* 사람 클래스만 필터링
* 바운딩 박스와 confidence 반환
* 영상 파일 및 웹캠 테스트

### 2단계: 사람 추적 (완료)

* ByteTrack 연동
* Track ID 반환
* 추적 결과를 프로젝트 내부 객체로 변환
* 순간 탐지 누락 처리

### 3단계: 사람 수 상태 머신 (완료)

* 0명, 1명, 2명 이상 구분
* 다중 인물 확인
* 한 명 복귀 안정화
* 일시적 추적 실패 처리

### 4단계: 화면상 위치 (부분 완료)

* 중심 좌표 계산
* 정규화 좌표 계산
* `LEFT`, `CENTER`, `RIGHT` 분류 — **만들지 않았다.** 같은 판정을 추종 희망 명령으로 대체했다(§4.5)
* 추가로 구현된 것: 추종 희망 명령 생성과 UDP 전송

### 5단계: 누운 자세 판단 (미착수)

* 침대 ROI 설정
* 바운딩 박스 기반 누운 자세 후보 판단
* 오탐 사례 기록

### 6단계: 움직임 분석 (미착수)

* 중심점 또는 ROI 변화량 계산
* 저움직임 유지시간 계산
* 자세 정보와 결합

### 7단계: 수면 및 상호작용 상태 머신 (미착수)

* `UNKNOWN`
* `AWAKE`
* `RESTING`
* `SLEEPING_ESTIMATED`
* 능동 대화 허용 여부 계산

### 8단계: ROS2 연동 (미착수 — 대신 UDP 경계를 채택했다)

* 이미지 Topic 구독
* 비전 상태 Topic 발행
* QoS 및 메시지 구조 합의
* 핵심 AI 로직과 ROS2 코드 분리

이 단계는 **다른 형태로 해결됐다.** ROS 2 노드를 이 패키지에 두는 대신 경계를 **UDP JSON**으로 긋고, ROS 2 노드는 `robot/ros2_ws/src/core`의 `vision_udp_bridge`가 갖게 했다. 그래서 `ai_vision`에는 `rclpy` import가 한 건도 없고 ROS 2 환경 없이 노트북에서 그대로 돌릴 수 있다 — 마지막 항목("핵심 AI 로직과 ROS2 코드 분리")은 가장 강한 형태로 충족된 셈이다. 다만 앞의 세 항목(이미지 Topic 구독, 비전 상태 Topic 발행, 커스텀 메시지·QoS 합의)은 여전히 없다. 프레임은 카메라에서 직접 읽고, 결과는 String 메시지로 중계된다.

### 9단계: Jetson 최적화 (미착수)

* 모델 크기 비교
* TensorRT 변환
* FPS 및 지연시간 측정
* 필요한 경우 Pose 실행 주기 조절

## 13. 기능별 수용 기준

각 수용 기준을 실제로 잠그고 있는 테스트는 다음과 같다. 기준을 바꾸려면 해당 테스트를 먼저 읽는다.

| 수용 기준 | 잠그는 테스트 | 상태 |
|---|---|---|
| §13.1 사람 탐지 | `tests/unit/test_person_detection.py` | 변환 로직만 검증 — 런타임 경로에 탐지 단계가 없다 |
| §13.2 사람 추적 | `tests/unit/test_tracking_adapter.py` | 부분 |
| §13.3 상태 머신 | `tests/unit/test_tracking.py` | 충족 |
| §13.4 수면 상태 | 없음 | 미착수 |
| §13.5 최종 파이프라인 | `tests/integration/test_position_pipeline.py`, `tests/test_primary_person.py` | 부분 |

`evals/`는 실제 영상 기반 품질 측정을 담기로 한 자리인데 아직 비어 있다. §13의 정확도성 기준 상당수가 그 디렉터리를 전제하므로, 지금 "충족"이라고 적힌 항목은 전부 단위 테스트 수준의 충족이다.

### 13.1 사람 탐지 완료 기준

* 사람이 없는 영상에서 빈 목록을 반환한다.
* 한 명의 사람이 있는 영상에서 사람 바운딩 박스를 반환한다.
* 사람 이외 객체를 보호대상자로 반환하지 않는다.
* confidence 임계값을 설정으로 변경할 수 있다.
* 잘못된 프레임 입력을 안전하게 처리한다.

### 13.2 사람 추적 완료 기준

* 동일한 사람이 연속 프레임에서 이동할 때 Track ID가 대체로 유지된다.
* Track ID가 없는 결과를 안전하게 처리한다.
* 사람을 놓친 한두 프레임으로 프로그램이 종료되지 않는다.
* 두 명의 사람에게 서로 다른 Track ID가 부여된다.

### 13.3 상태 머신 완료 기준

* 0명이 지속되면 `NOT_DETECTED`를 반환한다.
* 1명이 정상 검출되면 `TRACKING`을 반환한다.
* 두 명 이상이 순간 검출되면 `MULTIPLE_PENDING`을 반환한다.
* 두 명 이상이 기준 이상 지속되면 `MULTIPLE_PERSONS`를 반환한다.
* 다중 인물 상태에서 한 명으로 줄어들면 `SINGLE_RECOVERY`를 반환한다.
* 한 명이 안정적으로 유지되면 `TRACKING`으로 복귀한다.
* 음수 사람 수와 같은 잘못된 입력을 거부한다.

### 13.4 수면 상태 완료 기준

* 사람이 없으면 `UNKNOWN`을 반환한다.
* 다중 인물이면 `UNKNOWN`을 반환한다.
* 서거나 앉은 자세가 안정적으로 관찰되면 `AWAKE` 후보를 반환한다.
* 누운 자세가 일정 시간 지속되면 `RESTING`을 반환한다.
* 누운 자세와 저움직임이 기준시간 이상 지속되면 `SLEEPING_ESTIMATED`를 반환한다.
* 큰 움직임 또는 기립 자세가 지속되면 `AWAKE`로 복귀한다.
* `UNKNOWN`, `RESTING`, `SLEEPING_ESTIMATED`에서 능동 대화를 허용하지 않는다.

### 13.5 최종 파이프라인 완료 기준

* 영상 프레임 하나를 입력하면 구조화된 비전 결과를 반환한다. — **부분.** 조립 코드는 프레임 단위 함수가 아니라 루프 함수(`run_person_tracking`)이고 반환값 없이 결과를 뷰로 흘려보낸다. 프레임 단위 계약은 `UserTrackingService.update()`와 `FollowCommandGenerator.generate()` 수준에 있다.
* 외부 모델 객체가 최종 결과에 직접 포함되지 않는다. — **충족.** `domain/` 5개 파일 중 외부 라이브러리를 import하는 파일이 0개다.
* 오류 발생 시 안전한 결과를 반환한다. — **부분.** 상태·위치 결손은 `stop`으로 안전하게 떨어지지만, 카메라 읽기 실패는 안전 상태 전환 없이 루프를 끝낸다(§9).
* 설정값 변경을 위해 핵심 코드를 수정할 필요가 없다. — **CLI 인자 범위 안에서만 충족**(§8).
* 사람 탐지, 추적, 상태 판단을 개별적으로 테스트할 수 있다. — 충족.
* ROS2 없이도 영상 파일과 웹캠으로 기능을 검증할 수 있다. — **웹캠만 충족.** 영상 파일 입력 경로가 없다.

## 14. 확정 상태

### 14.1 확정된 항목

* YOLO 계열 모델을 이용해 사람을 탐지한다.
* ByteTrack을 이용해 프레임 간 사람을 추적한다.
* 정상 환경에는 보호대상자 한 명이 존재한다고 가정한다.
* 유효한 사람이 정확히 한 명이면 해당 사람을 보호대상자로 간주한다.
* 두 명 이상이 검출되면 특정 사람을 임의로 보호대상자로 선택하지 않는다.
* 다중 인물 상태에서는 능동 대화를 허용하지 않는다.
* 잠들었거나 쉬고 있을 가능성이 있으면 능동 대화를 허용하지 않는다.
* AI 비전 모듈은 모터와 TTS를 직접 제어하지 않는다.
* 얼굴인식과 Person Re-ID는 MVP에서 제외한다.

### 14.2 확정된 구현 값

| 항목 | 값 | 비고 |
|---|---|---|
| YOLO 모델 | `yolo11n.pt` | 노트북 MVP 기준. 젯슨 최적화(TensorRT)는 미착수 |
| 기본 confidence | `0.8` (코드) | 실기에서는 너무 높아 사람을 거의 잡지 못했다. launch는 `0.5`, 시연 스크립트는 `0.30`을 쓴다. `--confidence` 도움말 문자열이 `default: 0.5`로 잘못 출력되는 결함이 있다 |
| 다중 인물 확인 기준 | 연속 5프레임 | 시간 기준은 쓰지 않는다 |
| 한 명 복귀 안정화 기준 | 연속 10프레임 | |
| 일시적 추적 실패 허용 | 3프레임 | **시간이 아니라 프레임 수다.** 실기 launch·스크립트는 24 FPS를 감안해 12로 올린다 |
| 외부 인터페이스 | UDP JSON 4필드 | ROS 2 커스텀 메시지 대신 채택. §12 8단계 참고 |

### 14.3 구현 방법이 미확정인 항목

* 누운 자세 판별 방식
* 움직임 계산 방식
* 수면 및 휴식 상태 전환시간
* 대표 인물 선택을 요구사항으로 승격할지, 시연 전용 예외로 못박을지(§4.3)

### 14.4 기능 적용 여부를 검토 중인 항목

* 침대 또는 특정 공간 인식
* 침대 ROI 설정
* YOLO Pose 사용
* 수면 영상 데이터셋을 이용한 추가 학습
* Optical Flow 사용
* 별도의 자세 분류 모델 사용

검토 중인 항목은 활성 실행 계획에서 구현 대상으로 명시되기 전까지
필수 기능으로 취급하지 않는다.
