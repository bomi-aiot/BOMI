# BOMI AI Vision Agent Guide

## 1. 프로젝트 목적

이 저장소는 독거노인 또는 보호대상자를 위한 돌봄 로봇의 AI 비전 기능을 구현한다.

AI 비전 모듈의 주요 책임은 다음과 같다.

1. YOLO를 이용해 영상에서 사람을 탐지한다.
2. ByteTrack을 이용해 프레임 간 사람을 추적한다.
3. 정상 환경에서는 검출된 한 명의 사람을 보호대상자로 간주한다.
4. 두 명 이상이 검출되면 보호대상자를 임의로 선택하지 않고 예외 상태를 반환한다.
5. 정상 추적 중인 한 명의 화면상 위치로 추종 희망 방향을 만들어 주행 제어 모듈에 전달한다.
6. AI 비전 핵심 로직과 외부 시스템 연동 코드를 분리한다. 현재 연동 경계는 UDP JSON이며 ROS 2 노드는 `robot/ros2_ws/src/core` 패키지(`vision_udp_bridge`)가 소유한다. 이 패키지는 `rclpy`를 import하지 않는다.

다음 항목은 **설계만 있고 아직 구현하지 않았다.** 코드를 읽을 때 있다고 가정하지 않는다.

* 자세·움직임 분석과 사용자 상태(`AWAKE` / `RESTING` / `SLEEPING_ESTIMATED`) 추정
* 능동 대화 허용 여부(`interaction_allowed`)와 이동 허용 여부(`movement_allowed`) 계산
* YAML 설정 계층과 ROS 2 노드

이 시스템은 의료적인 수면 진단을 수행하지 않는다.

수면 관련 기능의 목적은 잠들었거나 쉬고 있을 가능성이 있는 사용자에게 로봇이 먼저 말을 걸지 않도록 하는 것이다. 이 목적은 유효하지만 구현은 시작되지 않았다.

## 2. 현재 MVP 운영 전제

현재 MVP에서는 다음 운영 조건을 전제로 한다.

* 정상 환경에는 보호대상자 한 명만 존재한다.
* 한 명이 검출되면 해당 사람을 보호대상자로 간주한다.
* 얼굴인식은 구현하지 않는다.
* Person Re-ID는 구현하지 않는다.
* 여러 사람 중 보호대상자를 선택하는 기능은 기본적으로 구현하지 않는다. 기본 동작은 "여러 명이면 대상을 정하지 않고 정지"다.
* 예외: `--select-primary-person`을 명시적으로 켠 경우에만 상태 머신 **앞에서** 후보를 한 명으로 줄인다. 기준은 신뢰도가 아니라 화면 중앙 최근접이며(동률이면 상자 높이, 그다음 Track ID), 조건을 통과한 후보가 없으면 원본 목록을 그대로 넘겨 "여러 명이면 정지" 규칙이 살아난다. 이 예외는 구경꾼이 있는 사람 추종 시연을 위해 도입했고 기본값은 꺼짐이다(`primary_person.py` 모듈 docstring에 결정 근거가 있다).
* 실제 생리학적인 수면 판정은 구현하지 않는다.
* AI 비전 모듈은 모터를 직접 제어하지 않는다.
* AI 비전 모듈은 TTS 또는 대화를 직접 실행하지 않는다.

## 3. 필수 참고 문서

작업자(사람 또는 에이전트)는 코드를 생성하거나 수정하기 전에 작업과 관련된 문서를 반드시 읽어야 한다.

기본적으로 다음 문서를 확인한다.

* `README.md`
* `ARCHITECTURE.md`
* `docs/code-style.md`
* `docs/vision-requirements.md`
* `docs/state-machine.md`

현재 진행 중인 작업이 있다면 다음 경로의 실행 계획도 확인한다.

* `docs/plans/active/` (현재 비어 있음)
* `docs/plans/completed/` — 이미 끝난 티켓의 실행 계획과 결정 기록 6건

위 문서들이 서로 어긋날 때는 **`README.md`와 소스 코드가 구현 사실의 기준**이고, `ARCHITECTURE.md`·`docs/vision-requirements.md`·`docs/state-machine.md`는 목표 상태를 기술한다는 점을 먼저 확인한다. 세 문서는 각자 절 단위로 구현 상태를 표기하고 있으므로 그 표기를 함께 읽는다.

구현 내용과 문서 내용이 충돌하면 임의로 결정하지 않는다.

충돌 사항을 현재 실행 계획의 미해결 항목에 기록하고, 기존 요구사항을 우선 유지한다.

## 4. 코드 작성 원칙

이 프로젝트는 다른 개발자가 처음 코드를 읽어도 목적과 흐름을 이해할 수 있는 코드를 우선한다.

모든 코드 작성과 수정은 `docs/code-style.md`를 따라야 한다.

필수 규칙은 다음과 같다.

### 4.1 한국어 설명 작성

* 모든 설명 주석과 docstring은 한국어로 작성한다.
* 변수명, 함수명, 클래스명, 모듈명은 영어로 작성한다.
* 주석은 코드 내용을 그대로 번역하지 않는다.
* 주석은 해당 코드가 존재하는 이유, 설계 의도, 주의사항을 중심으로 작성한다.
* 코드를 변경하면 관련 주석과 docstring도 함께 갱신한다.

### 4.2 파일 설명

모든 Python 파일의 최상단에는 한국어 모듈 docstring을 작성한다.

모듈 docstring에는 필요한 범위에서 다음 내용을 포함한다.

1. 파일의 목적
2. 주요 기능
3. 다른 모듈과의 관계
4. 주요 입력과 출력
5. 사용 시 주의사항

### 4.3 클래스 설명

모든 클래스에는 클래스 선언 직후 한국어 docstring을 작성한다.

클래스 docstring에는 다음 내용을 설명한다.

* 클래스의 책임
* 관리하는 주요 상태
* 주요 사용 방법
* 외부 라이브러리와의 관계

### 4.4 함수와 메서드 설명

모든 공개 함수와 메서드에는 한국어 docstring을 작성한다.

함수의 복잡도에 따라 다음 내용을 포함한다.

* 함수의 역할
* 입력값
* 반환값
* 발생 가능한 예외
* 상태 변경 또는 부작용
* 사용 시 주의사항

비공개 함수라도 함수명만으로 역할이나 설계 의도를 파악하기 어렵다면 한국어 docstring을 작성한다.

### 4.5 주요 변수 설명

다음 항목에는 한국어 주석을 작성한다.

* 모델 신뢰도 임계값
* 상태 전환 임계값
* 누적 프레임 수
* 시간 기준값
* 안전 정책에 영향을 주는 Boolean 값
* 좌표계 또는 단위가 중요한 값
* 이름만으로 목적을 이해하기 어려운 변수
* 모델 경로, Topic 이름 등 외부 환경에 영향을 받는 설정값

단순 반복문 인덱스나 이름만으로 의미가 명확한 지역 변수에는 불필요한 주석을 작성하지 않는다.

### 4.6 기본 개발 원칙

모든 기능 구현과 코드 수정에 다음 개발 원칙을 기본으로 적용한다.

#### KISS

현재 요구사항을 만족하는 가장 단순하고 명확한 구현을 우선한다.

* 같은 결과를 더 단순한 코드로 구현할 수 있다면 단순한 방식을 선택한다.
* 불필요한 계층, 래퍼, 인터페이스 및 디자인 패턴을 추가하지 않는다.
* 실행 흐름을 여러 파일과 함수 사이에 지나치게 분산하지 않는다.
* 코드를 처음 읽는 개발자가 입력, 처리, 출력을 쉽게 파악할 수 있어야 한다.

#### YAGNI

현재 Jira 이슈와 실행 계획에 없는 기능은 미리 구현하지 않는다.

* 미래에 필요할 수 있다는 이유만으로 빈 클래스나 인터페이스를 만들지 않는다.
* 아직 사용하지 않는 설정값, 상태, 예외 및 확장 지점을 추가하지 않는다.
* 실제 필요성이 확인되기 전에는 범용 프레임워크나 플러그인 구조를 만들지 않는다.
* 후속 기능은 현재 코드에 미리 포함하지 않고 별도의 Jira 이슈에서 구현한다.

#### 단일 책임

모듈, 클래스 및 함수는 하나의 명확한 책임을 가져야 한다.

* 카메라 입력, 모델 추론, 결과 변환, 상태 판단 및 외부 전송을 하나의 함수에 섞지 않는다.
* 코드가 짧고 책임이 동일하다면 불필요하게 파일을 분리하지 않는다.
* 변경 이유가 다른 기능은 서로 다른 모듈로 분리한다.
* 역할을 설명하기 어려운 모듈이나 클래스가 생기면 책임을 다시 검토한다.

#### 파이프라인 중심 설계

AI 비전의 주요 실행 흐름은 입력부터 출력까지 순서대로 읽을 수 있어야 한다.

권장 흐름:

```text
입력 수집
→ 모델 추론
→ 외부 모델 결과 변환
→ 도메인 판단
→ 최종 결과 반환 또는 발행
```

* application 계층은 각 단계를 조합하고 전체 흐름을 보여준다.
* application 계층에 외부 라이브러리의 세부 처리나 복잡한 계산을 직접 작성하지 않는다.
* 각 단계의 입력과 출력 타입을 명확히 한다.
* 중간 단계에서 외부 라이브러리 객체를 다른 계층으로 그대로 전달하지 않는다.

#### Contract-First

서로 다른 모듈 또는 담당 영역이 연결되는 기능은 구현 전에 입력과 출력 규격을 먼저 정의한다.

* 도메인 데이터 구조는 OpenCV, Ultralytics, PyTorch, TensorRT 및 ROS2 객체에 의존하지 않는다.
* 필드 이름, 타입, 좌표계, 단위, 값의 범위 및 실패 상태를 명확히 정의한다.
* 여러 사람이 검출되거나 입력이 유효하지 않은 상황을 계약에 포함한다.
* 규격이 문서와 충돌하거나 결정되지 않았다면 임의로 구현하지 않고 미해결 사항으로 기록한다.

#### 얇은 수직 기능 구현

큰 기능을 계층별로 한꺼번에 완성하려 하지 않고, 입력부터 출력까지 동작하는 가장 작은 기능을 먼저 구현한다.

예:

```text
카메라 프레임 입력
→ 사람 탐지
→ 프로젝트 탐지 결과 변환
→ 결과 화면 표시
```

* 모델 adapter만 만들고 실제 실행 흐름을 연결하지 않은 상태로 작업을 끝내지 않는다.
* 첫 구현에서는 최소 동작 경로를 완성한 뒤 실제 실패 사례를 기준으로 개선한다.
* 각 수직 기능은 하나의 Jira 이슈에서 완료하고 검증할 수 있는 크기로 나눈다.
* 정확도 최적화와 구조 확장은 기본 동작이 검증된 이후 진행한다.

#### 테스트 가능한 경계

외부 장비와 모델에 의존하는 코드와 순수한 판단 및 변환 로직을 분리한다.

* 카메라, 모델, ROS2 및 네트워크가 없어도 핵심 로직을 단위 테스트할 수 있어야 한다.
* 외부 라이브러리 결과는 adapter에서 단순한 프로젝트 데이터 구조로 변환한다.
* 좌표 계산, 필터링, 대상 수 판단 및 상태 전환은 외부 라이브러리 없이 테스트한다.
* 외부 객체 전체를 복잡하게 모방하는 테스트를 만들지 않는다.
* 구현 내부보다 외부에서 관찰되는 입력과 출력 동작을 검증한다.

### 4.7 원칙 적용 우선순위

위 원칙이 서로 충돌하는 경우 다음 순서로 판단한다.

1. 안전 기본값과 명시된 요구사항
2. `AGENTS.md`와 필수 참고 문서의 아키텍처 규칙
3. 현재 Jira 이슈와 실행 계획의 작업 범위
4. 이해하기 쉬운 단순한 구현
5. 테스트 가능성과 유지보수성
6. 미래 확장 가능성

미래 확장 가능성을 위해 현재 구현을 불필요하게 복잡하게 만들지 않는다.

## 5. 아키텍처 규칙

### 5.1 핵심 로직과 외부 기술 분리

도메인 및 상태 판단 로직은 다음 외부 라이브러리에 직접 의존하지 않아야 한다.

* ROS2
* OpenCV
* Ultralytics
* PyTorch
* TensorRT

외부 기술과 연결되는 코드는 adapter 계층에 배치한다.

### 5.2 의존성 방향

의존은 항상 바깥에서 안쪽으로만 향한다.

```text
adapters          OpenCV 카메라·디버그 창, Ultralytics 추적, UDP 송신
   │ 의존
   ↓
application       application.py (파이프라인 조립)
   │ 의존          tracking.py / position.py / follow.py / primary_person.py (판단)
   ↓
domain            detection / follow / position / tracking (외부 라이브러리 무의존)
```

`domain`은 `application`과 `adapters`를 알지 못하고, `application`은 `adapters`를 알지 못한다. 이 규칙은 실제로 지켜지고 있다 — `domain/` 5개 파일 중 외부 라이브러리를 import하는 파일은 0개이고, `cv2`/`numpy`는 `adapters/opencv.py` 한 곳, `ultralytics`는 어댑터 두 곳의 지연 import뿐이다.

판단 로직은 아직 별도 패키지가 아니라 `src/bomi_vision/` 최상위의 평면 파일이다. 파일이 늘어 경계가 흐려질 때 `application/` 패키지로 승격하고, 그전에는 만들지 않는다(§4.6 YAGNI). `detection` / `state` / `sleep` 이라는 중간 패키지는 존재하지 않는다.

### 5.3 역할 분리

* 추적 어댑터는 외부 모델(Ultralytics 통합 추적)을 한 번 호출해 프로젝트 데이터 구조로 변환한다. 현재 파이프라인에는 별도의 탐지 단계가 없다 — `UltralyticsPersonDetector`는 정의만 있고 호출되지 않는다.
* 상태 머신은 사람 수와 이전 상태로 추적 상태를 결정한다. 시각 입력은 쓰지 않는다.
* application 계층은 각 기능을 조합한다.
* adapter 계층은 카메라와 외부 시스템을 연결한다. **이 모듈의 유일한 외부 출력은 `adapters/udp.py`의 UDP JSON 4필드**(`status`/`command`/`track_id`/`reason`)이며, 포트 5005에서 `core` 패키지의 `vision_udp_bridge`가 받는다. 필드 이름과 값(소문자)은 외부 계약이므로 임의로 바꾸지 않는다.
* 수면 분석 모듈은 설계에만 있다. 자세·움직임 기반 상태 추정은 아직 구현되지 않았다.

### 5.4 직접 제어 금지

AI 비전 코드는 다음 동작을 직접 실행하면 안 된다.

* 모터 속도 변경
* `/cmd_vel` 직접 제어
* 로봇 비상 정지 실행
* TTS 실행
* 대화 시작
* Spring 또는 FastAPI 내부 비즈니스 로직 직접 호출

AI 비전은 관찰 결과와 상태만 반환하거나 발행한다.

실제 행동은 주행, 안전 제어, 대화 시스템이 결정한다.

## 6. 안전 기본값

AI 비전 결과가 불확실하면 안전한 방향으로 처리한다. 이것이 이 패키지에서 가장 중요한 규칙이다.

**현재 코드에서 이 규칙의 구현체는 `follow.py`의 정지 폴백이다.** `TRACKING`이 아닌 다섯 상태, 대표 위치 또는 Track ID 결손, 범위를 벗어난 위치값은 전부 `stop` 명령이 된다. 이전 프레임 위치로 이동을 이어가지 않는다. 같은 규칙이 `position.py`(두 명 이상이면 위치 계산 자체를 하지 않는다)와 `domain/tracking.py`(`TRACKING`은 `person_count == 1`일 때만 성립하며 생성자가 `ValueError`로 강제한다)에도 박혀 있다. **세 곳은 한 규칙의 세 얼굴이므로 하나만 풀면 안전망이 통째로 헐거워진다.**

다음 상황에서는 불확실한 것으로 보고 정지한다. 앞의 세 항목은 구현돼 있고, 뒤의 네 항목(자세·상태 추정)은 사용자 상태 분석이 도입될 때 적용할 목표다.

* 사람이 검출되지 않음 — 구현됨
* 두 명 이상이 검출됨 — 구현됨
* 한 명 상태로 복귀한 뒤 안정화 중 — 구현됨
* 내부 처리 오류 또는 유효하지 않은 위치값 — 구현됨
* 사용자의 자세를 판단할 수 없음 — 미구현
* 사용자가 누워 있음 / 쉬는 상태로 추정됨 / 잠든 상태로 추정됨 — 미구현
* 입력 영상이 오래됐거나 유효하지 않음 — 미구현(최신성 판정 개념이 없다)

"능동 대화 허용"(`interaction_allowed`)이라는 출력은 아직 존재하지 않는다. 이 모듈의 출력은 추적 상태와 추종 희망 명령뿐이며, 능동 대화 여부는 `ai_chat`이 결정한다.

한 프레임의 결과만으로 상태를 즉시 확정하지 않는다.

상태 전환에는 연속 프레임 수, 지속시간 또는 히스테리시스를 적용한다.

## 7. 설정값 관리

다음 값은 코드에 직접 하드코딩하지 않는다.

| 값 | 현재 주입 방법 |
|---|---|
| 모델 경로·종류 | `--model` |
| confidence 임계값 | `--confidence` |
| 카메라 번호 | `--camera` |
| 추적기 설정 | `--tracker` |
| 일시적 추적 실패 허용 프레임 수 | `--lost-tolerance-frames` |
| 다중 인물 확인 프레임 수 | `--multiple-confirm-frames` |
| 한 명 복귀 안정화 프레임 수 | `--single-recovery-frames` |
| 수평 중앙 허용 범위 | `--horizontal-dead-zone` |
| 전진 정지 높이 비율 | `--forward-threshold` |
| 대표 인물 선택 3종 | `--select-primary-person`, `--primary-min-confidence`, `--primary-min-height-ratio` |
| 디버그 영상 출력 여부 | `--no-window` (`udp_main` 전용) |
| UDP 목적지 | `--host`(또는 `BOMI_ROBOT_HOST`), `--port` |

**설정값은 현재 명령행 인자로만 주입한다.** YAML 설정 파일 계층은 존재하지 않으며(`config/`는 빈 디렉터리), 저장소 어디에도 YAML 파서 import가 없다. 설정 항목이 늘어 argparse로 감당하기 어려워지면 그때 설정 파일을 도입한다.

다음 값은 개념 자체가 아직 코드에 없다 — 입력 이미지 크기, 영상 파일 경로, 누운 자세 판정 임계값, 움직임 판정 임계값, 수면 상태 전환 시간, ROS 2 Topic 이름(ROS 2 노드가 이 패키지에 없다). 해당 기능을 구현할 때 위 규칙을 적용한다.

기본값이 필요한 경우 기본값의 선정 이유를 한국어 주석이나 문서로 설명한다. `main.py` 상단의 상수 주석이 이 규칙의 실제 사례다. 다만 **코드 기본값은 노트북 웹캠 확인용이고 실기 값과 다르다.** 실기 값과 그 차이의 이유는 `README.md`의 "실기에서 쓰는 값은 코드 기본값과 다르다" 표에 있다.

## 8. 테스트 규칙

새로운 기능을 구현하거나 기존 동작을 변경하면 관련 테스트도 함께 작성하거나 수정한다.

### 8.1 단위 테스트

다음 로직은 가능한 한 외부 모델 없이 단위 테스트할 수 있어야 한다.

* 사람 수에 따른 상태 전환 — `tests/unit/test_tracking.py`가 잠그고 있다
* 다중 인물 확인 로직 — 같은 파일
* 한 명 복귀 안정화 로직 — 같은 파일
* 일시적 추적 실패 처리 — 같은 파일
* 추종 희망 명령 판단 — `tests/unit/test_follow.py`
* 대표 인물 선택 — `tests/test_primary_person.py`
* 잘못된 입력 처리 — 도메인 계약 생성자와 파서 검증
* 수면 상태 전환, 능동 대화 허용 여부 — 해당 기능이 구현될 때 함께 만든다(현재 코드 없음)

### 8.2 통합 테스트

다음 흐름은 통합 테스트 대상으로 관리한다.

* 영상 프레임 입력
* 사람 탐지 결과 변환
* 추적 결과 변환
* 사람 수 계산
* 상태 머신 갱신
* 최종 비전 상태 반환

### 8.3 테스트 품질

테스트는 구현 세부사항보다 외부에서 관찰되는 동작을 검증한다.

테스트 이름은 영어로 작성하되 어떤 상황을 검증하는지 명확하게 표현한다.

## 9. 작업 절차

### 9.1 작업 시작 전

코드를 변경하기 전에 다음 절차를 수행한다.

1. 루트 `AGENTS.md`를 읽는다.
2. 현재 디렉터리에 추가 `AGENTS.md`가 있는지 확인한다.
3. 관련 요구사항 문서를 읽는다.

5. 기존 코드와 테스트를 확인한다.
6. 변경 대상과 변경하지 않을 범위를 구분한다.
7. 이번 작업에 4.6의 기본 개발 원칙을 어떻게 적용할지 확인한다.

### 9.2 구현 중

* 요청 범위를 넘어선 기능을 임의로 추가하지 않는다.
* 한 번의 작업에서는 하나의 명확한 목표에 집중한다.
* 외부 라이브러리의 세부 객체를 도메인 계층으로 노출하지 않는다.
* 중요한 판단과 상태 전환에는 한국어 설명을 작성한다.
* 오류를 무시하지 않고 안전한 결과로 변환한다.
* 사용되지 않는 코드나 미래 확장을 위한 추상화를 미리 만들지 않는다.

### 9.3 작업 완료 후

다음 항목을 수행한다.

1. 포맷 검사를 실행한다.
2. 린트 검사를 실행한다.

검증 명령을 실행하지 못했다면 실행한 것처럼 보고하지 않는다.

실행하지 못한 이유를 명확히 기록한다.

## 10. 기본 명령

프로젝트의 표준 명령은 다음과 같다.

* 개발 환경 설치: `make setup`
* 코드 포맷: `make format`
* 린트 검사: `make lint`
* 한국어 docstring 검사: `make check-docstrings`
* 단위 테스트: `make test-unit`
* 통합 테스트: `make test-integration`
* 전체 테스트: `make test`
* 전체 검증: `make check`

여덟 개 명령 모두 `Makefile`에 정의돼 있다. 다만 현재 상태를 알고 시작해야 한다.

* `make check-docstrings`는 **현재 34건의 위반으로 실패한다.** 대부분 `tests/test_primary_person.py`의 테스트 함수·가짜 클래스 docstring 누락이며, 이를 선행 의존으로 거는 `make check`도 함께 실패한다. §9.3과 §11이 이 명령들의 통과를 완료 조건으로 걸고 있으므로, 정리가 끝날 때까지는 **"내 변경이 새 위반을 추가하지 않았는가"**를 기준으로 삼는다. 기존 34건은 별도 작업으로 정리한다.
* `make test-unit`은 `pytest tests/unit -m unit`이라 `tests/test_primary_person.py`와 마커 없는 테스트를 수집하지 않는다. 전체 회귀를 보려면 `make test`를 쓴다.
* 테스트는 프로젝트 루트에서 실행한다. `conftest.py`가 없어 일부 테스트가 `from scripts...` 형태로 import하므로 현재 작업 디렉터리가 `sys.path`에 들어가야 한다.

동일한 작업을 위해 새로운 임시 명령을 만들기보다 프로젝트의 표준 명령을 우선 사용한다.

## 12. 금지 사항

다음 행동을 하지 않는다.

* 테스트를 삭제하거나 약화해 구현을 통과시키지 않는다.
* 사용자 승인 없이 요구사항을 변경하지 않는다.
* 여러 사람이 검출된 상황에서 임의로 한 사람을 선택하지 않는다. `--select-primary-person`은 이 조항의 유일한 예외이며(§2 참고), 임의 선택이 아니라 "화면 중앙 최근접"이라는 명시 기준을 쓰고 기본값은 꺼짐이다. 이 예외를 넓히거나 기본값을 켜지 않는다.
* Track ID를 실제 사용자 신원으로 취급하지 않는다.
* 의료적인 수면 판정이 가능한 것처럼 표현하지 않는다.
* AI 비전 코드에서 모터나 TTS를 직접 실행하지 않는다.
* 모델 경로와 환경별 값을 여러 파일에 중복 하드코딩하지 않는다.
* 코드와 일치하지 않는 오래된 주석을 남기지 않는다. 현재 저장소에 실물 위반이 하나 있다 — `main.py`의 `--confidence` 도움말이 `default: 0.5`를 출력하지만 실제 기본값은 `0.8`이다. 그 파일을 고칠 일이 생기면 함께 정리한다.
* 코드 동작을 그대로 한국어로 번역한 불필요한 주석을 작성하지 않는다.
* 검증하지 않은 결과를 검증 완료로 보고하지 않는다.
