# BOMI 기술 소개 - 영상·GIF 촬영 지시서

> 목표: PPT 담당자가 기술을 몰라도 원본 영상을 받아 바로 장표에 배치할 수 있게 합니다.  
> 라이브 시연은 선택 사항이고, 발표 기본 경로는 **사전 녹화본**으로 설계합니다.

## 1. 공통 촬영 규칙

### 화면 규격

- 원본: 1920×1080, 30fps, MP4 H.264
- 화면 비율: 16:9
- 권장 길이: 한 클립 6~12초
- 시작과 끝에 0.5초 정지 프레임을 남깁니다.
- 실제 음성이 중요한 클립은 MP4, 상태 변화만 보는 클립은 GIF로 사용합니다.
- GIF 변환 시 960×540, 12~15fps, 2회 이하 반복을 권장합니다.

### 모든 영상에 넣을 두 자막

1. 왼쪽 위: 관객이 봐야 할 행동 한 줄
2. 오른쪽 아래: 검증 범위 라벨

검증 범위 라벨은 다음 중 하나만 사용합니다.

- `실물 구동`
- `Simulation`
- `실센서 → Gazebo`
- `실 API`
- `Mock Data`
- `코드 동작`

### 촬영 금지

- API key, 비밀번호, MQTT username, DB 접속정보
- 실제 어르신 개인정보, 실제 대화 원문, 전화번호, 주소
- 개인 PC 사용자명과 경로가 불필요하게 드러나는 터미널
- 브라우저 탭·북마크·메신저 알림
- 실패 로그가 계속 쌓이는 화면을 성공 영상처럼 사용

### 장면 편집 규칙

- 마우스가 메뉴를 찾아 헤매는 시간을 제거합니다.
- 한 클립에서 관객이 볼 포인트는 하나만 둡니다.
- 속도를 높여야 하면 입력 구간만 1.5~2배속하고 결과 상태는 정상 속도로 둡니다.
- 로그는 3줄 이상 보이지 않게 확대합니다. 전체 터미널을 보여주지 않습니다.
- 실제와 Simulation을 한 화면에 섞으면 각 영역 위에 라벨을 따로 붙입니다.

# 2. 필수 촬영 목록

## A01. 웨이크워드와 이어지는 대화 - 선택

- 담당: AI Chat
- 파일명: `APPX_wakeword_multiturn_v1.mp4`
- 길이: 10~12초
- 라벨: `실물 음성` 또는 실제 장비가 아니면 `개발 PC 음성`
- 목적: 버튼 없이 이름을 부르고, 한 번 시작한 뒤 후속 질문이 이어지는 경험을 보여줍니다.

### 촬영 순서

1. 1초간 아무 말도 하지 않습니다.
2. “보미야”라고 부릅니다.
3. 호출 응답이 끝난 뒤 짧은 질문을 합니다.
4. BOMI가 답한 뒤 후속 질문을 한 번 더 합니다.
5. 두 번째 답변의 첫 문장까지 보여주고 끝냅니다.

### 자막

```text
“보미야”에만 깨어나고, 한 번 시작하면 대화가 이어집니다
```

### 주의

- 현재 대화 루프는 BOMI 발화가 끝난 뒤 다시 듣는 구조입니다.
- 말하는 중간에 끼어드는 장면을 만들지 않습니다.
- 원거리 소음 환경 성능을 주장하지 않습니다.
- 15초 무응답·마무리 발화로 세션이 끝나는 장면은 부록용으로 별도 촬영할 수 있습니다.

## A02. MQTT 명령에서 Nav2 도착 결과까지

- 담당: Backend + Robot
- 파일명: `T09_mqtt_nav2_arrived_v1.mp4`
- 길이: 8~10초
- 라벨: `Simulation`
- 목적: 센서·백엔드·로봇이 사건번호로 연결된다는 것을 증명합니다.

### 화면 구성

- 왼쪽 25%: MQTT 명령에서 `type=NAVIGATE`, `target=ENTRANCE`, 짧은 scenarioId만 표시
- 중앙 50%: RViz 또는 Gazebo 경로와 이동
- 오른쪽 25%: `NAVIGATION_RESULT`, `ARRIVED`, 같은 scenarioId 표시

### 촬영 순서

1. 세 화면을 미리 띄우고 확대율을 고정합니다.
2. 명령 한 건만 발행합니다.
3. RViz 경로가 생기는 순간부터 로봇이 도착할 때까지 촬영합니다.
4. 도착 결과가 뜬 프레임을 1초 유지합니다.

### 주의

- `DEFAULT` 복귀까지 영상에 넣으려면 해당 목적지가 지원되는지 먼저 확인합니다.
- 브리지의 기본 driver가 mock인지 반드시 확인합니다. mock이면 `Simulation 이동` 증거로 사용할 수 없습니다.
- Nav2와 사람 추종을 동시에 실행하지 않습니다.
- 외부 TLS broker보다 로컬 broker 시뮬레이션이 발표용으로 안전합니다.

## A03. 능동 발화 게이트

- 담당: AI Chat + PPT
- 파일명: 실제 영상이 아니라 PPT native animation으로 제작
- 장표: T10~T14
- 라벨: `코드 동작`
- 목적: 복약·일정·인사·안부 중 한 번에 하나만 선택하고 침묵도 정상 결과임을 설명합니다.

### 준비할 데이터

- 복약 카드: `20:00 혈압약 알림`
- 일정 카드: `내일 10:00 병원`
- 인사 카드: `현관 귀가 인사`
- 안부 카드: `오래 대화가 없었음`

### 애니메이션

1. 네 카드가 `대화 문지기` 앞에 모입니다.
2. `유효시간`, `조용한 시간`, `쿨다운`, `중요도` 필터가 차례로 나타납니다.
3. 복약 카드 하나만 커집니다.
4. 다른 카드는 뒤로 이동해 대기합니다.
5. 다른 예시에서는 통과 카드가 없어 스피커가 꺼집니다.

### 주의

- TV와 실제 대화를 구분하거나 수면을 인식하는 그래픽을 넣지 않습니다.
- 실제 사용자 행동을 학습해 최적 시간을 자동 예측한다고 표현하지 않습니다.

## A04. 일반 통증과 위험 가능성 비교

- 담당: AI Chat
- 파일명: `T16_ordinary_vs_safety_v1.mp4`
- 길이: 10~12초
- 라벨: `코드 동작` 또는 실제 마이크면 `개발 PC 음성`
- 목적: 모든 통증을 응급으로 보거나 모두 일반 대화로 보내지 않는 구조를 보여줍니다.

### 촬영 순서

1. 새 세션에서 “무릎이 아파”라고 말합니다.
2. 일반 공감 응답과 일반 대화 경로 로그를 짧게 보여줍니다.
3. 화면을 전환해 새 세션에서 “가슴이 아파”라고 말합니다.
4. 고정 확인 질문이 나오는 장면을 보여줍니다.
5. `safety_triage → safety_confirm` 경로를 화면 하단 자막으로만 표시합니다.

### 자막

```text
일반 대화보다 먼저, 안전 가능성을 별도 경로에서 확인
```

### 촬영 전 필수 확인

- 자동 테스트가 초록인지 확인합니다.
- 두 발화가 기대 경로로 실제 분기되는지 리허설합니다.
- 현장 점검 결과가 없거나 불안정하면 실제 음성 영상 대신 PPT 구조 애니메이션만 사용합니다.

### 주의

- `응급 정확 탐지`, `의료 진단`, `119 신고` 자막을 넣지 않습니다.
- 불안감을 높이는 사이렌 효과음을 사용하지 않습니다.

## A05. 네트워크 단절과 outbox

- 담당: AI Chat + Backend
- 파일명: `T20_outbox_retry_v1.mp4`
- 길이: 7~9초
- 라벨: `코드 동작`
- 목적: 안전 알림을 전송 전에 먼저 보관하고 재시도하는 구조를 보여줍니다.

### 권장 촬영 방식

실제 네트워크를 끊는 라이브보다 테스트 또는 로컬 시뮬레이션 로그를 녹화합니다.

1. T1 알림을 생성합니다.
2. outbox row가 생기는 것을 1줄로 보여줍니다.
3. 전송 실패 로그를 한 줄 보여줍니다.
4. 연결 복구 후 전송 성공과 outbox 상태 변경을 보여줍니다.

### 자막

```text
전송보다 저장이 먼저 - 연결되면 다시 전달
```

### 주의

- 실제 보호자 push가 도착하는 것처럼 연출하지 않습니다.
- payload에 사용자 발화 원문이 포함되지 않았는지 확인합니다.

## A06. 보호자 확인 요청 핵심 플로우

- 담당: Frontend + Backend
- 파일명: `T26_confirmation_decision_v1.mp4`
- 길이: 10~12초
- 라벨: `실 API` 권장. 불가능하면 `Mock Data`
- 목적: AI가 정리한 사실을 사람이 근거와 함께 결정하는 장면을 보여줍니다.

### 촬영 순서

1. 대시보드 `보미가 확인을 기다려요` 카드를 확대합니다.
2. 확인 요청 페이지로 이동합니다.
3. `대화 근거`, `현재값`, `제안값`을 차례로 스크롤 없이 보여줍니다.
4. `확정`을 클릭합니다.
5. 성공 토스트와 확인 건수 감소를 보여줍니다.
6. 가능하면 5초 내 `되돌리기`를 클릭해 복원까지 보여줍니다.

### 자막

```text
AI는 제안하고, 사람은 확정합니다
```

### 촬영 전 설정

- `VITE_USE_MOCK_API=false`로 실 API 모드를 쓰는 것이 가장 좋습니다.
- Mock이면 상단의 예시 데이터 배너를 자르지 말고 라벨도 `Mock Data`로 둡니다.
- JSON 직접 편집 화면은 비전문 관객에게 어려우므로 `확정` 또는 `다시 질문`을 사용합니다.

### 주의

- WebSocket/SSE/polling이 없으므로 외부 이벤트 뒤에는 수동 새로고침이 필요합니다.
- 실제 사용자 개인정보를 촬영하지 않습니다.
- undo는 현재 서버 재시작을 넘는 영속 기능이 아닙니다.

## A08. 한 명 → 두 명 → STOP → 복귀

- 담당: AI Vision + Robot
- 파일명: `T34_person_1to2_stop_v1.mp4`
- 길이: 8~10초
- 라벨: `실센서 → Gazebo`
- 목적: BOMI 비전 기술에서 가장 인상적인 안전 전환을 보여줍니다.

### 화면 구성

- 왼쪽: 실제 카메라 디버그 화면과 상태·Track ID
- 오른쪽: Gazebo 로봇과 `/cmd_vel`
- 중앙 하단: 현재 상태를 큰 단어로 표시

### 촬영 순서

1. 한 명이 화면 중앙에서 시작합니다: `TRACKING`.
2. 왼쪽으로 이동해 `TURN_LEFT`가 나오는 장면을 보여줍니다.
3. 두 번째 사람이 들어옵니다: `MULTIPLE_PENDING`부터 STOP.
4. 두 명 상태가 확정됩니다: `MULTIPLE_PERSONS`, 계속 STOP.
5. 다시 한 명만 남습니다: `SINGLE_RECOVERY`, 잠시 STOP.
6. 안정화 뒤 `TRACKING`으로 돌아옵니다.

### 자막

```text
누구인지 확실하지 않으면 임의로 선택하지 않고 정지
```

### 주의

- Track ID는 얼굴 인식·신원 확인이 아닙니다.
- 실제 모터를 움직인 영상처럼 크롭하지 않습니다. Gazebo 영역과 라벨을 유지합니다.

## A09. LiDAR가 AI 전진 명령을 덮는 장면

- 담당: Robot
- 파일명: `T33_lidar_override_v1.mp4`
- 길이: 6~8초
- 라벨: `실센서 → Gazebo`
- 목적: 카메라 AI보다 하위 안전 센서가 최종 우선권을 가진다는 것을 보여줍니다.

### 촬영 순서

1. 카메라가 중앙의 먼 사람을 보고 `MOVE_FORWARD`를 냅니다.
2. Gazebo 로봇이 전진하는 장면을 짧게 보여줍니다.
3. 실제 X4 LiDAR 앞에 가까운 장애물을 둡니다.
4. 카메라 명령은 그대로인데 최종 `/cmd_vel`이 0이 되고 로봇이 멈춥니다.

### 자막

```text
AI: 앞으로 / LiDAR: 정지 → 최종 결과: STOP
```

### 주의

- 장애물을 갑자기 던지거나 센서에 충격을 주지 않습니다.
- 실제 안전거리 수치를 크게 주장하려면 환경에 맞는 재측정이 필요합니다.

## A10. 실물 모터와 Pico watchdog

- 담당: Robot
- 파일명: `T35_pico_watchdog_v1.mp4`
- 길이: 6~8초
- 라벨: `실물 구동`
- 목적: 실물에서 확인된 구동과 하위 정지를 정직하게 자랑합니다.

### 촬영 순서

1. 넓고 안전한 공간에서 낮은 속도로 전진합니다.
2. 바퀴 또는 차체가 움직이는 것이 분명하게 보이게 합니다.
3. 명령 발행을 중단합니다.
4. 로봇이 멈추고 watchdog/timeout 로그가 뜨는 장면을 분할 화면으로 보여줍니다.

### 자막

```text
명령이 끊기면 Pico 단계에서 정지
```

### 안전

- 바퀴를 띄운 상태의 bench test를 먼저 수행합니다.
- 사람과 벽에서 충분히 떨어진 공간에서 촬영합니다.
- 긴급 전원 차단 담당자를 한 명 둡니다.
- 현재 tread 보정과 관성 회전 이슈를 고려해 제자리회전 종료 직후 가까이 접근하지 않습니다.

# 3. 선택 촬영 목록

## B01. 일정 생성과 사후 안부

- `새 일정 추가 → 한 시간 뒤 진료 → 미리 알림 ON → 사후 질문 ON → 저장`
- 파일명: `APPX_schedule_followup_v1.mp4`

- 주의: 로봇이 실제로 질문하는 영상과 FE 설정 영상은 별도 컷입니다.

## B02. 복약 등록

- `복약 추가 → 이름·용량·시간 → 음성 알림 ON → 카드 생성`
- 파일명: `APPX_medication_create_v1.mp4`
- 목적: 건강 데이터는 보호자가 약 봉투·처방을 확인해 입력한다는 흐름을 보여줍니다.
- 주의: `응답 없음 = 미복용`으로 표시하거나 말하지 않습니다.

## B03. SLAM 타임랩스

- 빈 RViz 지도에 벽이 생기는 과정을 4~6초로 압축합니다.
- 파일명: `APPX_slam_timelapse_v1.mp4`
- 라벨: `Simulation` 또는 `실물 LiDAR 수동 이동`
- 주의: `실제 집 자동 매핑 완료`라고 쓰지 않습니다.

## B04. 자동 테스트 증거

- 각 영역의 최신 테스트를 발표 직전에 실행한 뒤 마지막 summary만 캡처합니다.
- 코드 전체나 긴 로그를 보여주지 않습니다.
- `자동 테스트`라는 단어를 수치 옆에 반드시 붙입니다.
- 실행하지 않은 문서 기록을 `통과` 수치로 사용하지 않습니다.

# 4. 발표 당일 재생 리스크 줄이기

## PPT 안에 넣는 방식

- 외부 링크 대신 PPTX 내부에 미디어를 삽입합니다.
- `자동 시작`, `전체 화면 재생 아님`, `재생 후 되감기`를 설정합니다.
- 첫 프레임이 검은 화면이 되지 않도록 poster frame을 지정합니다.
- GIF는 발표 노트북에서 실제 재생 속도를 확인합니다.
- 동영상 압축 후 글자가 뭉개지면 로그 영역을 더 크게 크롭합니다.

## 백업

- 모든 영상의 `MP4 원본`, `GIF 대체본`, `마지막 프레임 PNG`를 준비합니다.
- 재생 실패 시 발표자가 같은 문장을 말할 수 있도록 장표에 핵심 상태 자막을 남깁니다.
- 라이브 시연용 계정·데이터와 녹화용 고정 데이터를 분리합니다.
- 발표 직전 새 기능을 넣은 영상을 사용하지 않습니다. 최종 리허설에서 검증된 파일을 잠급니다.

## 최종 체크

- [ ] 영상에 개인정보·비밀키가 없음
- [ ] 모든 영상에 검증 범위 라벨이 있음
- [ ] Simulation과 실물이 섞여 보이지 않음
- [ ] 첫 장면과 마지막 장면이 0.5초 유지됨
- [ ] 자막만 읽어도 무엇을 봐야 하는지 알 수 있음
- [ ] PPT에 파일이 포함되어 오프라인에서도 재생됨
- [ ] 동영상이 실패해도 마지막 프레임 PNG로 설명 가능
- [ ] 실제 시연 대사와 영상 타이밍을 최소 3회 맞춰봄
